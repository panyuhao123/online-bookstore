# 线上书店 APP —— 数据库设计说明书（DBD）

| 项目 | 内容 |
| --- | --- |
| 数据库 | MySQL 8.0（`bookstore`） |
| 字符集 | utf8mb4 / utf8mb4_general_ci |
| 版本 | V1.0 |
| 文档日期 | 2026-10-16 |

---

## 1. 设计约定

1. **只建业务外键，不建物理外键**：避免级联锁、便于数据迁移与分库扩展，一致性由应用层事务保证。
2. **金额一律 `DECIMAL(10,2)`**：不使用 FLOAT/DOUBLE，杜绝浮点精度误差。
3. **逻辑删除优先**：用户、图书、评价均通过 `status` 字段标记失效，保留审计痕迹。
4. **审计字段**：所有表保留 `create_time`，可变表同时保留 `update_time`（`ON UPDATE CURRENT_TIMESTAMP`）。
5. **快照冗余**：订单保存地址快照与商品快照（书名/封面/单价），保证历史订单可还原、不被后续编辑污染。

## 2. 实体关系（ER）

```
user ──1:N──> cart ──N:1──> book
user ──1:N──> orders ──1:N──> order_item ──N:1──> book
user ──1:N──> review ──N:1──> book
                     └──N:1──> orders
category ──1:N──> book
admin ──1:N──> operation_log
user ──1:N──> browse_history ──N:1──> book

```

## 3. 表结构

### 3.1 `user` —— APP 用户表

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT | PK, 自增 | 主键 |
| phone | VARCHAR(20) | NOT NULL, UNIQUE | 登录账号 |
| password | VARCHAR(64) | NOT NULL | 密码密文：BCrypt（新数据，固定 60 字符）或历史 MD5(明文 + salt) |
| salt | VARCHAR(32) | NOT NULL | 历史遗留盐值；BCrypt 数据下为空串（盐已编码进密文） |
| nickname | VARCHAR(50) | | 昵称 |
| avatar_url | VARCHAR(500) | | 头像 |
| status | TINYINT | NOT NULL, 默认 1 | 1-正常 0-禁用 |
| create_time / update_time | DATETIME | NOT NULL | 审计 |

索引：`uk_user_phone`（唯一）、`idx_user_status`。

> **密码存储（演进说明）**：系统早期按需求文档实现为 `MD5(明文 + 8 位随机盐)`，
> 能防彩虹表但无法抵御 GPU 离线爆破——MD5 是"快哈希"，加盐并不改变这一点。
> 现改为 **BCrypt**（自适应慢哈希，代价因子 10，盐内置于密文）。
> 由于 BCrypt 密文固定 60 字符，可原样存入既有 `password VARCHAR(64)` 列，**无需改表**；
> `salt` 列保留但新数据写入空串，历史数据继续沿用旧盐值。
> 迁移策略为**登录时惰性升级**：`PasswordUtil` 依据密文格式自动选择校验算法，
> 老账号在首次登录成功后由服务层就地重写为 BCrypt，用户无感、无需强制改密。

### 3.2 `admin` —— 管理员表

与 `user` 分离：后台仅单一管理员角色，避免角色体系复杂化。字段同构于 `user`，唯一键 `uk_admin_username`。

### 3.3 `category` —— 图书分类表

`name` 唯一（`uk_category_name`）；`sort` 控制前台展示顺序，索引 `idx_category_sort`。

### 3.4 `book` —— 图书表

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| category_id | BIGINT | 业务外键 → category.id |
| title / author / publisher | VARCHAR | 书名 / 作者 / 出版社 |
| price | DECIMAL(10,2) | 单价 |
| stock | INT | 库存 |
| cover_url | VARCHAR(500) | 封面地址 |
| description | TEXT | 简介 |
| sales | INT | 销量（后台编辑图书时不覆盖该值） |
| status | TINYINT | 1-上架 0-下架 |

索引设计：

| 索引 | 用途 |
| --- | --- |
| `idx_book_status_cate_price (status, category_id, price)` | 覆盖"上架 + 指定分类 + 价格区间"这一最典型前台筛选组合 |
| `idx_book_sales` | 热销榜、默认排序走索引，避免临时表排序 |
| `idx_book_title` | 书名精确/前缀匹配 |
| `ft_book_search (title, author)` FULLTEXT | 书名/作者全文检索（ngram 分词） |

### 3.5 `cart` —— 购物车表

唯一键 `uk_cart_user_book (user_id, book_id)`：同一用户对同一本书只保留一条记录，重复加入累加 `quantity`。`checked` 标记是否勾选，下单只取已勾选条目。

### 3.6 `address` —— 收货地址表

`is_default` 标记默认地址；索引 `idx_address_default (user_id, is_default)` 加速"取默认地址"查询。

另有 `province_adcode` / `city_adcode` / `district_adcode`（`VARCHAR(12)`，可空）三列，保存省市区的高德 adcode 编码。省市区选择器与地理编码接口以编码为稳定标识（名称会变、编码不会），下单时的完整地址仍以 `orders.address_snapshot` 为准，故这三列不影响订单数据。

> 这三列曾是手工直接改库添加、既不在 `db/schema.sql` 也不在任何迁移脚本中 —— 由 `verify_flyway_migration.py` 的结构比对守卫检出后补为 `V5__address_adcode_columns.sql`。

### 3.7 `orders` —— 订单主表

| 字段 | 说明 |
| --- | --- |
| order_no | 订单编号，唯一，对外展示 |
| total_amount | **商品小计**（不含运费），语义与存量数据保持一致，未被改写 |
| freight_amount | 运费金额（`V6` 新增）。**应付金额 = total_amount + freight_amount**，由应用层相加 |
| status | **1-待支付 2-已支付 3-已发货 4-已完成 5-已取消** |
| address_snapshot | 下单瞬间的收件人/电话/完整地址快照 |
| pay_time | 支付时间（模拟支付写入） |
| ship_time | 发货时间（`V6` 新增，管理端发货时写入） |
| finish_time | 完成时间（`V6` 新增，用户确认收货时写入） |

> **为什么不让 `total_amount` 直接含运费**：存量订单的 `total_amount` 语义就是商品小计，
> 改写语义会让历史数据对不上账。因此新增独立列，应付金额由 `total_amount + freight_amount` 得出。
>
> **为什么必须补 `ship_time` / `finish_time`**：订单时间线（待支付→已支付→已发货→已完成）
> 此前只能用 `update_time` 近似，而 `update_time` 会被任何一次无关更新刷新，
> 时间线上会出现「发货时间晚于收货时间」这类看起来像 bug 的展示。运费与时间线一并落在 `V6`。

### 3.8 `order_item` —— 订单明细表

冗余 `book_title`、`book_cover`、`price`，`subtotal = price * quantity`。冗余的意义：图书后续改价、改标题不影响历史订单的可读性与可对账性。

### 3.9 `review` —— 图书评价表（迁移 `V4__book_review.sql`）

| 字段 | 说明 |
| --- | --- |
| book_id / user_id / order_id | 评价对象 / 评价人 / 来源订单 |
| rating | 1~5 星 |
| content | 评价内容 |
| anonymous | 1-匿名（前台隐藏昵称，后台不做匿名） |
| status | 1-正常 0-已隐藏 |

关键约束：

- 唯一键 `uk_review_user_book_order (user_id, book_id, order_id)`：**同一订单内同一本书只能评价一次**，从数据层排除刷评；允许同一用户在不同订单中分别评价同一本书（均构成真实购买）。
- 索引 `idx_review_book_status_time (book_id, status, create_time)`：主查询路径"某本书的正常评价按时间倒序"。
- 隐藏而非删除：违规评价 `status=0` 后立即从前台列表与平均分中消失，数据保留可追溯、可恢复。

### 3.10 `operation_log` —— 管理端操作日志表（迁移 `V3__operation_log.sql`）

记录 `admin_id`、`admin_name`（名称快照，防止改名后无法追溯）、`module`、`action`、`uri`、`params`（敏感字段脱敏、超长截断）、`ip`、`duration_ms`、`success`、`error_msg`。索引 `idx_oplog_create_time` 支撑后台按时间倒序分页。



### 3.11 本轮新增的 6 张表（迁移 `V6__booklist_history_banner_freight.sql`）

写这 6 张表的直接动因是：PC 商城此前有六项功能**没有后端支撑** ——
「书单 / 浏览历史 / 图书对比」的数据只存在浏览器 `localStorage` 里，
「首页 Banner」是三条写死在页面里的渐变，「免运费 / 商品目录」则完全没有实现。
落到数据库后，「换台电脑数据还在」与「后台可维护」才成立。

#### `book_list` —— 用户书单主表

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT | PK, 自增 | 主键 |
| user_id | BIGINT | NOT NULL | 创建者（业务外键 → `user.id`） |
| name | VARCHAR(50) | NOT NULL | 书单名称（同一用户内不允许重名） |
| description | VARCHAR(200) | | 简介 |
| cover_url | VARCHAR(500) | | 封面（为空时前端按首本书封面兜底） |
| is_public | TINYINT | NOT NULL, 默认 1 | 1-公开 0-仅自己可见 |
| book_count | INT | NOT NULL, 默认 0 | 冗余计数，列表页免 `count` |
| status | TINYINT | NOT NULL, 默认 1 | **平台治理状态**：1-正常 0-已隐藏（`V7` 新增，与 `is_public` 语义正交） |
| create_time / update_time | DATETIME | NOT NULL | 审计 |

索引：`idx_book_list_public_time (is_public, create_time)`（书单广场主路径）、`idx_book_list_user (user_id)`（"我的书单"）、`idx_book_list_status_time (status, create_time)`（`V7` 新增，管理端治理主路径）。

> **`status` 与 `is_public` 为什么必须是两列**
>
> `is_public` 回答的是「用户愿意给谁看」，`status` 回答的是「平台允不允许展示」。二者语义正交，
> 必须能独立取值 ——「用户设了公开」+「平台已隐藏」是合法组合。
>
> 如果把治理实现成「隐藏时把 `is_public` 改成 0」，恢复时就没有任何依据还原用户当初的选择，
> 只能一律按公开处理，等于替用户改了设置。因此隐藏只写 `status`，`is_public` 一个字节都不动。
>
> 状态取值沿用 `review` 表的既有约定（1-正常 0-已隐藏），并同样遵循**隐藏优先于删除**：
> 隐藏后前台立即不可见、数据仍在，可追溯、可申诉、可恢复；物理删除只留给垃圾数据清理。

#### `book_list_item` —— 书单条目表

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT | PK, 自增 | 主键 |
| list_id | BIGINT | NOT NULL | 书单（业务外键 → `book_list.id`） |
| book_id | BIGINT | NOT NULL | 图书（业务外键 → `book.id`） |
| sort | INT | NOT NULL, 默认 0 | 书单内排序，越小越靠前 |
| create_time | DATETIME | NOT NULL | 加入时间 |

索引：`uk_book_list_item (list_id, book_id)` 唯一 —— **在数据库层兜住"同一本书在一个书单里只能出现一次"**，应用层再查一次只是为了给出友好提示，不依赖应用层判断的正确性；`idx_book_list_item_book (book_id)` 支持反向查询"某本书被哪些书单收录"。

#### `browse_history` —— 浏览历史表

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT | PK, 自增 | 主键 |
| user_id | BIGINT | NOT NULL | 用户（业务外键 → `user.id`） |
| book_id | BIGINT | NOT NULL | 图书（业务外键 → `book.id`） |
| view_time | DATETIME | NOT NULL | 最近一次浏览时间 |

索引：`uk_browse_history_user_book (user_id, book_id)` 唯一 —— 让"重复浏览同一本书"退化为一次 upsert，天然去重；`idx_browse_history_user_time (user_id, view_time)` 服务"我的浏览历史倒序"主路径。

> **上限不写进表约束**：100 条上限属于可调的业务策略，由应用层在写入后裁剪（先查主键再批量删）。
> 写成触发器或约束后调整就得改表，而这条数值大概率会随使用量再变。

#### `banner` —— 首页轮播图表

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT | PK, 自增 | 主键 |
| title | VARCHAR(50) | NOT NULL | 主标题 |
| sub_title | VARCHAR(100) | | 副标题 |
| image_url | VARCHAR(500) | | 背景图；**为空时前端回退渲染 `bg_color`** |
| bg_color | VARCHAR(120) | | 无图时的背景色/渐变 |
| link_url | VARCHAR(200) | | 跳转路径（站内路径或外链） |
| sort | INT | NOT NULL, 默认 0 | 排序，越小越靠前 |
| status | TINYINT | NOT NULL, 默认 1 | 1-上架 0-下架 |
| create_time / update_time | DATETIME | NOT NULL | 审计 |

索引：`idx_banner_status_sort (status, sort)`（前台唯一查询路径）。
初始数据把原先写死在 `home/index.vue` 里的三条渐变搬进库，迁移后首页观感不变，但从此可在管理端增删改。

#### `stock_notice` —— 缺货到货提醒订阅表

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT | PK, 自增 | 主键 |
| user_id | BIGINT | NOT NULL | 订阅用户（业务外键 → `user.id`） |
| book_id | BIGINT | NOT NULL | 图书（业务外键 → `book.id`） |
| status | TINYINT | NOT NULL, 默认 0 | **0-待通知 1-已通知 2-已取消** |
| notify_time | DATETIME | | 通知时间（后台标记已通知时写入） |
| create_time | DATETIME | NOT NULL | 订阅时间 |

索引：`uk_stock_notice_user_book (user_id, book_id)` 唯一 —— 取消后重新订阅**复用该行**（`status` 改回 0）而不是物理删除后重插，否则反复订阅/取消会不断产生新行、唯一键也就失去意义；`idx_stock_notice_book_status (book_id, status)` 支撑管理端"按图书聚合待通知人数"这条主路径。

> 这张表的真正价值在管理端：「这本书有多少人在等」直接指导补货优先级，
> 而它的展示口径是**按图书聚合**而非原始订阅流水 —— 运营打开页面想回答的是"先补哪本书"。

#### `sys_config` —— 系统配置（key-value）

| 字段 | 类型 | 约束 | 说明 |
| --- | --- | --- | --- |
| id | BIGINT | PK, 自增 | 主键 |
| config_key | VARCHAR(64) | NOT NULL, UNIQUE | 配置键（如 `freight.free-threshold`） |
| config_value | VARCHAR(200) | NOT NULL | 配置值，统一按字符串存、读取方自行转换 |
| description | VARCHAR(200) | | 说明，管理端展示 |
| editable | TINYINT | NOT NULL, 默认 1 | 1-可改 0-只读展示 |
| update_time | DATETIME | NOT NULL | 更新时间 |

唯一键 `uk_sys_config_key`。初始数据为运费规则三项（`freight.enabled=1`、`freight.free-threshold=99`、`freight.base-fee=8.00`）。

两条刻意的设计约束：

1. **只提供"列出"与"改值"，不提供新增与删除**。配置项的意义是"代码里有一处固定逻辑在读它"；
   若允许后台随意新增一个键，它永远不会被任何代码读到，只会成为一条看着有用、实则无人消费的数据。
   删除更危险 —— 键没了，读配置的代码会静默回落到默认值，运营却以为自己改过的东西还在生效。
   **新增配置属于发版动作，改值才是运营动作。**
2. **这张表刻意不加缓存**（与 `banner` 等以 `@Cacheable` 缓存的读多写少表相反）：它只有个位数行、
   读取成本可忽略，而一旦加了缓存就会出现"后台改了前台还读旧值"的一致性问题 ——
   `verify_extended_features.py` 专门断言了"改门槛后前台立刻跟随"这条链路。
3. `application.yml` 的 `bookstore.freight.*` 仅作为**库里读不到时的兜底默认值**，
   保证配置表被清空也不会让下单流程报错。

## 4. 数据一致性策略

| 场景 | 策略 |
| --- | --- |
| 防超卖 | `UPDATE book SET stock = stock - n WHERE id = ? AND stock >= n`，以影响行数判定成败 |
| 下单 | 单事务内写 `orders` + `order_item` + 扣库存 + 清理已勾选购物车 |
| 缓存一致性 | Cache-Aside：写操作失效缓存（清理动作注册到**事务提交后**执行，回滚则不清理，详见概要设计说明书）；Redis 不可用时熔断降级，直接回源数据库 |
| 评价计分 | 评价写入后刷新图书平均分；无有效评价时 `avgRating` 返回 `null` 而非 0 |
| 删除约束 | 已产生订单的图书只能下架不能删除；分类下存在图书时禁止删除 |

## 5. 结构版本管理与建库方式

### 5.1 权威来源：Flyway 迁移脚本

数据库结构的**唯一权威来源**是后端仓库中的迁移脚本，服务启动时自动执行：

| 脚本 | 作用 |
| --- | --- |
| `bookstore-server/src/main/resources/db/migration/V1__init_schema.sql` | 建 8 张基础表（user、admin、category、book、cart、address、orders、order_item） |
| `.../V2__book_filter_indexes.sql` | `book` 表筛选索引（`idx_book_status_cate_price`、`idx_book_sales`） |
| `.../V3__operation_log.sql` | 新增 `operation_log` |
| `.../V4__book_review.sql` | 新增 `review` |
| `.../V5__address_adcode_columns.sql` | `address` 表补 3 个 adcode 列 |
| `.../V6__booklist_history_banner_freight.sql` | 新增 `book_list`、`book_list_item`、`browse_history`、`banner`、`stock_notice`、`sys_config` 6 张表；`orders` 补 `freight_amount` / `ship_time` / `finish_time` 3 列 |
| `.../V7__book_list_status.sql` | `book_list` 补 `status`（平台治理：1-正常 0-已隐藏）与 `idx_book_list_status_time (status, create_time)` |

关键配置（`application.yml` 的 `spring.flyway`）：

| 配置项 | 值 | 作用 |
| --- | --- | --- |
| `locations` | `classpath:db/migration` | 迁移脚本目录 |
| `baseline-on-migrate` | `true` | 已有库首次启动时打基线，而不是从 V1 重跑（否则会撞 `CREATE TABLE` 报错） |
| `baseline-version` | `5` | 已有库的现状已等价于跑完 V1~V5，故基线到 5 |
| `validate-on-migrate` | `true` | 启动时校验脚本与历史记录一致，防止脚本被改动后静默跳过 |
| `clean-disabled` | `true` | 禁止 `clean`，防止误清库 |

**为什么保留 `db/schema.sql`**：它是**结构快照**（手工建库路径），不是权威来源。保留它的价值是双工具链冗余 + 便于人工阅读整体结构；同时用 `tools/verify_flyway_migration.py` 把快照与实际库逐表/逐列/逐索引/逐类型比对，任一侧漂移都会报错。

### 5.2 两种建库方式

| 方式 | 步骤 | 适用 |
| --- | --- | --- |
| **推荐：交给 Flyway** | ① `CREATE DATABASE bookstore ...`；② 启动后端 —— Flyway 自动把结构建好 | 新环境、换机器、答辩现场重装 |
| 手工快照（保底） | 依次执行 `db/schema.sql`、`db/seed.sql` | 无后端启动条件时快速铺数据 |

口令请用 `--defaults-extra-file` 传入（命令行中的口令字面量可能被运行环境改写，导致"错口令也连得上"的假阳性），用完即时删除临时文件：

```bash
mysql --defaults-extra-file=<临时配置文件> -e "CREATE DATABASE IF NOT EXISTS bookstore DEFAULT CHARSET utf8mb4 COLLATE utf8mb4_general_ci;"
mysql --defaults-extra-file=<临时配置文件> bookstore < db/seed.sql   # 仅需演示数据时
```
