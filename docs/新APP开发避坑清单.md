### 0.3 五类根因聚类

| 根因 | 涉及条目 | 共性结论 |
|---|---|---|
| **A. 契约未前置** | 1、11、17 | 「HTTP 恒 200 / 错误码 / 分页结构 / 文档分组」这类约定，一旦后端开始写就必须定死，否则每换一层框架都要重新适配 |

| **C. 平台与框架能力未先验** | 5、6、10、12、13、19、20、21、22 | 「以为支持、实际不支持」「以为生效、实际静默失效」——凡依赖他人实现，必须先写一个最小验证。**新增的 21/22 属于同一模式的变体：报错信息指向 A，真正的病根在 B**（单测说「实体找不到」实为元数据没注册；装测试框架失败实为 peer 依赖不匹配） |
| **D. UI 规范与临时原型滞后/返工** | 7、8、18 | Token 与原型策略是后置成本放大器；无后端支撑的假功能是演示可信度杀手 |

## 1. 立项前必须定死的事项（P0，写完签字）

### 1.1 需求边界

- [ ] **明确「不做清单」**，并承诺变更走流程：本项目初始定了「不做收藏/优惠券/积分/推送/在线阅读/退款」，后期因答辩需要加回「评价」——这本身不是错误，但应识别为**一次需求变更**：需要同步补表、补接口、补后台页、补 APP 页、改需求追溯矩阵。加一个需求 = 动五个地方。
- [ ] **单一需求源（SSOT）**：本项目同时存在 ima 知识库 SRS 与 `docs/需求规格说明书.md`，靠「冲突时以前者为准」兜底。**新项目只允许一份**，并用 `需求—实现追溯矩阵` 把每条需求映射到具体文件，取消需求时同步删除，避免「文档说有 / 代码没有」或反之。
- [ ] **写清演示与现实的分界**：模拟支付、假数据、占位图必须在立项时就写明哪些是模拟、切换真实需要什么（本项目把支付宝实现写完但如实标注「未与沙箱真实交互」，这是正确做法）。

### 1.2 数据模型（先冻结，再写代码）

- [ ] **一次性列全实体清单**，不要指望后期加表无痛。本项目初版 8 表漏了两类：
  - 审计类：`operation_log`（后台写操作留痕）；
  - 内容类：`review`（评价）。
  教训：**凡是「后台有人点」的系统，默认就要有操作日志表；凡是「UGC 内容」，默认就要独立表，不要塞进主表字段**。
- [ ] **每张表统一带**：`create_time`、`update_time`（自动填充）、软删除/状态字段、乐观字段按需。公共字段用 MyBatis-Plus 元对象处理器统一填，不要在业务代码里手写。
- [ ] **每个核心实体画状态机**，并作为验收依据。本项目订单状态到收尾才补齐闭环：`待支付 → 已支付 → 已发货 → 已完成` + `→ 已取消`，中间一度「已发货」是终态。
- [ ] **快照字段策略**：金额统一 `DECIMAL(10,2)`；订单冗余书名/封面/单价、收货地址快照；**明确哪些字段是快照（不可被后续编辑影响）**。
- [ ] **结构变更交给迁移工具，不要散落在手工脚本里**：本项目把手工幂等脚本（`information_schema` 判断 + `DELIMITER` 存储过程）换成了 Flyway 版本化脚本 `db/migration/V*.sql`。两个理由：① Flyway 保证每个版本只跑一次，「幂等」由工具负责，不必在 SQL 里写判断 —— 而且 Flyway 的 SQL 解析器**不支持 `DELIMITER` / `CREATE PROCEDURE`**，旧写法根本搬不过去；② 版本化后能看出「结构是怎么长出来的」，而不是一堆「当前状态」互相覆盖。已有库用 `baseline-on-migrate` + `baseline-version` 打基线接入（跳过历史、不动数据），全新库从 V1 顺序跑完。
- [ ] **保留的手工建库路径要有守卫**：本项目同时保留 `db/schema.sql` 作结构快照，并写脚本把它与实际库**逐表/逐列/逐索引/逐字段类型长度精度**比对 —— 这个守卫当轮就检出 3 个「手工直接改库、从未进入任何脚本」的漏网字段。两条建库路径并存时，没有守卫必然漂移。

### 1.3 前后端契约（写第一个接口之前）

- [ ] **统一返回体**：`{code, message, data, timestamp, requestId}`，HTTP 恒 200，成败只看 `body.code`。这条必须在写第一行代码前定；否则每接入一层新框架（本项目是 Spring Security，换了就得再写一层 401/403 转换器）都要重新适配一次。
- [ ] **错误码表落文档**：200/400/401/403/404/409/422/500 各自语义与示例文案。
- [ ] **分页结构统一**：`PageVO{list,total,pageNum,pageSize,pages}`，`pageSize` 上限保护**只写一处**（本项目抽 `BasePageQuery` 后才堵住「新查询 DTO 抄漏保护」）。
- [ ] **字段序列化约定（最容易被忽略，代价却最高）**：
  - 金额：`BigDecimal` 返回 `211.0` → 约定统一两位小数**字符串**或前端统一格式化，二选一，不要两边各写一半；
  - 时间：`LocalDateTime` 默认输出 `2026-10-16T10:48:07.825062` → 约定统一 `yyyy-MM-dd HH:mm:ss`；
  - **null 语义**：「无评价」返回 `null` 而非 `0`（0 分和暂无评分是两件事）。
- [ ] **VO 不含敏感字段**（password / salt），从第一天起，不做「先返回以后再删」。
- [ ] **列表接口必须返回前端渲染所需的全部字段**。判断标准：写页面时若需要为了渲染再发一次请求，就是后端字段不全（本项目订单列表缺 `items` 就是典型）。
- [ ] **前端→后端的错误三分类**：网络失败（拿不到响应）/ 业务失败（`code != 200`）/ 结构异常。各自的处理话术写死在 request 层。

### 1.4 技术与环境

- [ ] **第三方依赖分级**：必须（MySQL）/ 可降级（Redis）/ 可选（MinIO）。**可降级项必须有降级路径并有实测证据**——本项目杀掉 Redis 后所有接口仍 200 且数据正确，这一点值得保留为标配。
- [ ] **演示环境默认零依赖**：存储默认 `local`、支付默认 `mock`，需要展示高级能力时再切开关。
- [ ] **本机环境变量命名加项目前缀**，避免被运行环境注入的同名变量命中（本项目 `SERVER__PORT` → `server.port`）。
- [ ] **锁定依赖版本并核对该版本 API**，不要用较新版本的记忆写代码（MyBatis-Plus 3.5.7 是 `selectBatchIds`，3.5.9+ 才是 `selectByIds`）。

## 2. 开发过程必须遵守的约束

### P0（不做就会返工）

1. **平台差异先查表再写代码**。本项目 `<picker mode="region">` 在 App/H5 端明确不支持，官方推荐自行填充数据——一周后才发现。规则：**用到任何一个「看起来很方便」的官方组件前，先看文档的平台支持矩阵，App 端不支持就立刻换方案**。
2. **结构性 UI 改造要先列连锁影响清单**。移除原生 tabBar → `switchTab` 全失效 / 固定底栏互相遮挡 / 原生下拉刷新盖住自绘导航。规则：**凡改动导航模型、布局模式（fixed / custom 导航），先全局搜索相关 API 与定位类，列出受影响文件清单再动手**。
3. **没有后端支撑的假功能一律不做**。本项目的「客服中心」最终变成硬编码弹窗，演示时一眼看穿。规则：**功能必须有对应接口，接口不存在就砍需求，不做壳**。
4. **面向用户文案禁止出现技术话术**。「请确认 config.js 的 IP 正确」→「网络连接失败，请检查网络后重试」。排查信息只进 `console.error`。
5. **每个能力的验收脚本与代码同时提交**。本项目 258 项断言全绿的 `tools/verify_*.py`，是答辩当天唯一敢现场演示的底气。**没有脚本的能力 = 没有验证过的能力**。
6. **早于 Controller 抛出的异常必须单独处理**。`MaxUploadSizeExceededException`（参数解析阶段）不处理会落到兜底变成 500「服务器繁忙」。规则：**上线前把所有 500 都当作缺陷排查一遍**。

### P1（规范执行即可省下返工）

7. **禁止 N+1**：列表里要显示关联信息，一律「一次批量 IN + Map 回填」。本项目在分类名、订单明细、评分聚合、用户订单统计四处都按此写，无一踩坑。
8. **金额与时间的一致性规则只能有一处实现**。服务端负责算准（口径写进注释：销售额只含哪些状态），前端只在渲染层格式化，不在计算层重复实现金额逻辑；一旦前后端都在算，口径漂移只是时间问题。
9. **缓存策略按收益决定，且必须验证配置真的生效**。本项目两条硬经验：
   - 「写失效」优于「双写」：写库成功、写缓存失败会让用户看到错误的购物车数量；
   - **包装框架对象会改变其生命周期语义**：把 `RedisCacheManager` 包进自定义 `CacheManager` 后，它不再是 Bean，`initializeCaches()` 不执行，per-cache TTL 被静默忽略（5 分钟配成了 30 分钟）。规则：**包装第三方 Bean 之后，写一个断言把它的配置实测出来**（如 `TTL key` 必须等于 300）。
10. **管理端「菜单手写」必须有同步 Checklist**：新增页面 = 改 `router` + 改 `layout` 菜单 + 改 Knife4j 分组 + 改需求追溯矩阵。四处缺一就会出现「页面存在但没人找得到」。
11. **文档验收用「计数」而非「能打开」**。Knife4j 分组漏 `/api/review/**` 时文档照样能开，只是少了 5 个接口。规则：**每次交付核对「分组接口数 == 代码里统计的接口数」**。
12. **UI Token 从第一个页面起就用**。色值/字号/圆角/间距集中在 `uni.scss`，页面禁止硬编码。本项目把 14 个页面清一遍硬编码的代价，远大于一开始就用变量。
13. **Mock 数据必须一眼可辨 + 单一入口**。本项目 mock 图书主键从 10001 起配 `isMockId()` 判定，封面统一走 `cover.js`。规则：**Mock 只允许通过一个模块进入业务代码，且要写明是否会在交付前清退**。
14. **真机才是验收标准，模拟器与静态检查都不算**。CSS 图形、自绘导航层级、原生弹层、`@error` 是否触发，这四类只有在真机上才暴露。
15. **给 Service 写单测时，MyBatis-Plus 的实体元数据要手动注册**。不启动容器（纯 Mockito）时，`new LambdaUpdateWrapper<Orders>().set(Orders::getStatus, ...)` 会抛 `MybatisPlusException: can not find lambda cache for this entity [cn.edu.bookstore.entity.Orders]`。**报错信息极具误导性** —— 它看起来在说「这个实体类找不到」，实际是「lambda→列名的翻译表（`TableInfo`）没注册」，而那张表平时由 Mapper 扫描时顺带建立。修法（一次性写个支撑类复用）：
    ```java
    TableInfoHelper.initTableInfo(new MapperBuilderAssistant(new MybatisConfiguration(), ""), Orders.class);
    ```
    另一个配套坑：断言条件构造器的 SQL 时，`getSqlSegment()` 只含 WHERE 部分，`setSql(...)` 写进去的赋值在 **`getSqlSet()`** 里 —— 只断言前者会得到「看起来漏了一半」的结果。两者都要先做归一化（去反引号 + 压缩空白）再比对。
16. **判断「测试是否真的跑全了」，要比对文件数，不能只看断言总数**。第 23 条返工就是这个坑：受限环境（写临时目录被拒）下 vitest 抛 unhandled error 并中断收集阶段，3 个 spec 只跑了 2 个，汇总行却是 `Tests 12 passed, 0 failed` —— **数字漂亮且不含失败**。规则：门禁里同时记录「实际跑到的文件数」与「仓库里的 spec 文件数」，不一致就单独提示「覆盖不完整」。同时把「测试失败」（必须红）与「覆盖不完整」（需人看一眼、不影响退出码）**分成两种状态**，否则环境抖动会被误判成代码缺陷。
17. **vitest 默认的 `forks` 池会让「同一临时文件被并发写」**。vite 会把 `/@vite/env` 这个虚拟模块落到 `os.tmpdir()/<projectId>/<mode>/<sha1>`，vitest 内部有「同一路径只写一次」的去重表，但**那张表不跨进程** —— `forks` 下多个 worker 会并发写同一个文件。把 `pool` 改成 `'threads'`（同进程共享去重表）即根治，本项目管理端用例少，开销可忽略。定位手法值得记：错误里的文件名是 `sha1(模块 id)`，对候选 id（如 `/@vite/env`）算一遍 sha1 就能反查出到底是哪个模块。
18. **引入前端测试框架先核对 peer 依赖，别顺手升级构建工具**。`vitest@5` 要求 `vite@^6.4 || ^7 || ^8`，而项目是 `vite@5` → `npm i -D vitest` 直接 ERESOLVE。此时正确做法是**降级测试框架**（`vitest@2.1.9` 的 peer 是 `vite@^5`），而不是为了装测试把整个项目的构建工具升一个大版本 —— 后者会把「加测试」变成「重构构建链」。
19. **解析第三方 CLI 的输出前先剥 ANSI 颜色码**。vitest 在管道（非 TTY）下也照样上色，形如 `\x1b[2m      Tests \x1b[22m \x1b[1m\x1b[32m22 passed\x1b[39m`；肉眼在终端里看到的整整齐齐的 `Tests  22 passed (22)`，在程序读到的字符串里是被转义码切开的，`Tests\s+(\d+)` 这类正则**整行失配**。统一用 `re.sub(r"\x1b\[[0-9;]*[A-Za-z]", "", text)` 剥一遍再解析。
20. **测试框架/校验脚本不要把产物写到仓库外的固定目录**（如 `D:/tmp/xxx`）。既污染机器、又让脚本隐式依赖外部路径；写进项目内 `.tmp/` 并加进 `.gitignore` 才是可复现的做法。另外「先整目录 `rmSync` 再重建」在受限环境下会撞上批量删除护栏而整体失败，而校验脚本往往只需要一个「能覆写同名中转文件」的落脚点 —— 直接复用目录、不预删更稳。

### P2（锦上添花但成本很低）

21. **性能量化先定方法学**：多次采样取 **min**，冷调用前删缓存强制回源。用「首次 vs 中位」测到的是 JIT 预热，本项目据此一度得出「缓存负提升」的错误结论。
22. **跨页面通信谁注册谁注销**：`uni.$off(name)` 不带回调会移除全局所有同名监听，只能由注册方 `$off(name, handler)`。
23. **每日收尾生成开发日志**：进度 / 问题与根因 / 解决方法 / 待办 / 待确认决策点。本项目的日志在复盘时是唯一可信素材。
24. **收尾时必须做一次交付物盘点**（功能完成度 ≠ 交付完成度）。本项目功能 90% 时，APK 未打出、论文为 0、文档失真、AlipaySigner 未被调用。

## 4. 决策复盘：哪些当初是对的，哪些本应规避

### 4.1 做对且应保留的决策

| 决策 | 为什么对 |
|---|---|
| **不用第三方 UI 库（uView）**，官方组件 + 自写 CSS | 零依赖、出问题时排查面最小；代价要接受的只是多写 CSS |
| **HBuilderX 标准结构而非 CLI** | 双击即开、真机运行与打包不依赖 npm 环境；毕设场景的风险最低路径 |
| **统一返回体 + requestId + 全局异常处理** | 前端只需一套错误处理分支；requestId 让日志与客户端报错可一一对应 |
| **HTTP 恒 200 + body.code**（虽然定得晚） | APP 端判断逻辑单一，真机最稳；代价是不符合 REST 语义，属明示取舍 |
| **密码用 BCrypt，且登录时惰性升级旧密文**、登录失败统一文案 | BCrypt 自带盐、代价可调，能扛住离线爆破；`PasswordUtil` 按密文格式自动选算法，老账号登录成功后就地重写，无需停机迁移、不用强制用户改密。统一文案防止账号枚举 |
| **改哈希算法时，别把「校验」写死成单一算法** | 若登录只认 BCrypt，存量 MD5 用户会全体登录失败。必须先"识别格式 → 分流校验 → 成功后再重写"，且重写失败只告警不阻断登录 |
| **别把「有验证码」当成「防住了暴力破解」** | 验证码只能挡无脑脚本；"取验证码 → OCR → 猜密码"完全绕得过去，人工慢速尝试更是毫无阻碍。必须另加**按账号维度的失败计数 + 临时锁定**。锁定检查要放在口令校验之前，否则锁定了还能继续试 |
| **限流维度选账号，别选 IP** | 公司/校园网出口 IP 被大量用户共用，按 IP 限流会把"一个人输错密码"变成"整栋楼登不上"。IP 维度只适合作为辅助，且阈值要放宽 |
| **防超卖用条件 UPDATE，不先查后改** | 由数据库保证原子性，并发下不会卖超；影响行数为 0 即回滚，不会出现「有订单没库存 / 有扣减没订单」 |
| **金额/地址/书名做快照** | 后续改价改名下架都不污染历史订单 |
| **存储抽象 + 本地默认，MinIO 可选** | 演示现场零依赖；`@PostConstruct` 失败只告警，避免「MinIO 没起 → 整个后端起不来」的连锁故障 |
| **支付做成抽象层 + 默认 mock 实现** | 答辩零依赖；真实渠道切换只改配置，不动业务代码 |
| **购物车缓存用写失效而非双写** | 一致性 > 命中率；用户看到自己购物车数量错误是不能妥协的场景 |
| **结构变更用迁移工具纳管** | Flyway 保证每版本只跑一次，幂等交给工具；已有库打基线接入不丢数据，全新库一条命令建好 —— 换台机器不再靠"记得跑哪几个脚本" |
| **缓存清理要放在事务提交后** | 默认 `@CacheEvict` 在「方法返回后、事务提交前」执行 —— 缓存已清、事务未提交，此刻并发读会把**旧值**回填进缓存，提交后脏值一直存活到 TTL 到期。做法：把 `CacheManager` 再包一层，写操作注册到事务同步、只在 `afterCommit()` 落地，回滚则一律不动。**别直接用 Spring 的 `TransactionAwareCacheManagerProxy`** —— 它的 `afterCommit` 不吞异常，Redis 在提交后失败会把异常抛给「业务其实已提交成功」的调用方，且此时已脱离缓存切面、`CacheErrorHandler` 兜不住 |
| **改造要留一条"关掉新行为"的开关** | 缓存清理时机这类改动一旦上线就影响全站读一致性。挂一个配置开关（`bookstore.cache.evict-after-commit`）后，能用同一个代码库起两个实例做对照验证，真出问题可一行配置回退，也让"新旧行为差异"变成可实证的结论而不是口头断言 |
| **微秒级时序用单测验，别让端到端背这个锅** | 「事务提交前 vs 提交后清缓存」的窗口在微秒级，HTTP 层无法稳定复现 —— 用端到端断言时机会得到随机结果。正确分工：**单测**手工激活事务同步、精确控制「提交前 / 提交后 / 回滚」三个时点；**端到端**只验证行为、形态与不回归 |
| **「没有后端支撑的功能就砍掉」** | 功能真实性是演示可信度的基础 |
| **无状态 JWT 也要能「退出即失效」** | 只靠客户端删令牌，服务端在过期前仍认它 —— 令牌被复制走就能继续用。做法：签发时写入 `jti`，退出时把 `jti` 写入 Redis 黑名单（TTL = 令牌剩余有效期），过滤器逐请求校验。存储里只留「已失效」的少量条目，常态几乎为空，不需要把每个会话都存起来 |
| **令牌吊销要区分「收紧访问」与「放开访问」** | Redis 故障时，登录失败计数降级到本地内存（功能仍完整）；而黑名单必须**降级放行**并告警 —— 若一律拒绝，就把一次运维故障放大成全站用户被踢下线。同时黑名单降级窗口越小越好（本项目设 60 秒自动重试），因为期间其他实例吊销的令牌在本实例仍可用 |
| **登出接口必须幂等，且不能被吊销校验拦住** | 登出的目标是「让这枚令牌不可用」，本来就不可用时目标已达成，应返回成功。实践中踩到：过滤器命中黑名单就直接 401，导致重复点两次退出登录第二次报错。修法是把登出路径排除在吊销校验之外，而不是让前端去 catch |
| **别签发「永久令牌」** | `exp` 缺失的 JWT 永远不会过期，等于一把永久钥匙。校验时应显式要求 exp 存在（防御性校验，成本几乎为零），并在启动配置里给有效期设上限（本项目拒绝 > 720 小时） |
| **验证脚本的断言要写完再校准，别顺手写个「看起来对」的** | 本项目两次踩到：断言 `/api/book/list`（真实路径是 `/api/book/hot`）导致假失败；断言「带已失效令牌访问公开接口应 200」也写反了 —— 公开接口免登录不等于「接受任何凭证」，已吊销的凭证在任何接口上都应当被拒 |
| **验证脚本作为交付物的一部分** | 答辩现场一键复跑，比任何口头保证都有力 |
| **运维端点默认「全开」是最常见的裸奔** | actuator 一旦引入，`env`（含配置与口令占位）、`heapdump`（含内存中的密钥）、`beans` 就都能匿名下载。本项目只放行 `health`/`info`，其余 `/actuator/**` 要 ADMIN 角色，且**生产只暴露 `health`**。放行清单显式枚举，绝不写 `/actuator/**` 图省事 |
| **「有权限」与「有端点」是两件事** | 验证时要分清 401（没登录）、403（登录了没权限）、404（端点压根没开）。本项目实测：匿名访问 `/actuator/env` → 401；带 ADMIN 令牌访问 → 404。**404 才是真正的「最小暴露」证据**，只测 401 会把「忘记收敛端点」误判为「已保护」 |
| **健康检查别把「已降级」写成 DOWN** | 缓存熔断时业务已降级走数据库、对外仍可用。若健康检查判 DOWN，负载均衡会把本来能服务的实例摘掉，一次 Redis 抖动就被放大成全站不可用。本项目 `CacheHealthIndicator` 恒返回 UP，只把 `degraded=true` 写进明细 |
| **指标标签绝不能放高基数字段** | 把手机号、订单号、用户 ID 写进标签，会为每个取值创建一个时间序列，直接打爆指标后端。标签只用低基数枚举（本项目仅 `scope` / `result` / `role`） |
| **别为了打指标而重复造框架已有的轮子** | Spring Boot 的 `http.server.requests` 已经给出每个接口的调用量与耗时分布；业务埋点只补框架看不到的（登录成败、令牌吊销、下单、支付），不必自己写一遍接口计时 |
| **日志格式要按环境分流，且文件名必须是 `logback-spring.xml`** | 叫 `logback.xml` 时 `<springProfile>` 不生效，profile 分支形同虚设。同时注意：一旦定义了 `logback-spring.xml`，`application.yml` 里的 `logging.pattern.*` 会被静默忽略 —— 那是**死配置**，容易让人以为改了格式其实没改 |
| **结构化日志的首要要求是「一条 = 一行」** | 多行堆栈会让按行切分的采集端（Filebeat/Fluent Bit）把一次异常拆成多条残缺记录。编码器必须把异常栈转义进单个 JSON 字段，并在行尾补 `\n` |
| **链路 ID 要写进 MDC，而不是只在业务日志里手拼** | 写进 MDC 后，日志编码器统一取值，连连接池、参数校验器等**框架组件**的日志也自动带上 `requestId`，排障时才能真正串起一次请求的全过程 |
| **信息类端点只报「开关」不报「值」** | `/actuator/info` 适合输出「支付渠道=mock、令牌有效期=24、锁定是否开启」，但绝不能输出密钥、口令、私钥。写测试时要加**反向断言**（全文不含 secret/password/privateKey），否则很容易在后续迭代中不知不觉泄露 |
| **断言要挑「能失败的」方向** | 验证可观测性时，只断言「指标能读到」是弱断言（配置全错也可能恰好读到别的指标）。本项目改为「操作前记录计数 → 触发一次 → 再读」，断言**恰好 +1**，才能证明埋点真的接在了该接的地方 |
| **端到端断言多 ≠ 覆盖好，核心 Service 的单测不能省** | 本项目端到端有 414 项断言，但「库存恰好不足」「影响行数为 0」「地址越权」「状态被抢先变更」这些分支在 HTTP 层根本无法精确构造。补完单测后（123 → 192 项）这些分支才第一次被真正覆盖。**数字与覆盖是两件事，写论文时要分开陈述** |
| **门禁要区分「测试失败」与「覆盖不完整」** | 若把「只跑了 2/3 个测试文件」也算通过，覆盖不足会伪装成绿灯；若算失败，环境抖动会被误判成代码缺陷。正确做法：失败影响退出码，「覆盖不完整」列入「需留意」单独提示，并且**完整性靠比对文件数判断**（断言总数在这里帮不上忙） |
| **减少手工步骤，比强调纪律更有效** | 回归从「手工五步（起依赖 / 起服务 / 等就绪 / 逐个跑脚本 / 手动加总）」变成一条命令后，「漏跑某个脚本」「跑在错误实例上」这两类问题从「靠人记得」变成「结构上不可能发生」 |
| **给项目引入测试框架时，先对齐 peer 依赖** | `vitest@5` 要求 `vite@^6.4+`，项目是 `vite@5` → 装不上。此时应降级测试框架（`vitest@2.1.9`），而不是为了加测试把整个构建链升一个大版本 —— 后者会让「加测试」变成「重构构建链」 |
| **别让「不报错的测试」成为盲区** | vitest 默认 `forks` 池下，多个 worker 并发写同一个临时文件会让收集阶段中断，**汇总行依然显示全绿**。改用 `threads` 池（同进程共享写去重表）根治；并顺手在门禁里加「文件数比对」兜住同类问题 |
