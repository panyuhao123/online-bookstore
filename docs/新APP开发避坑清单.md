### 0.3 五类根因聚类

| 根因 | 涉及条目 | 共性结论 |
|---|---|---|
| **A. 契约未前置** | 1、11、17 | 「HTTP 恒 200 / 错误码 / 分页结构 / 文档分组」这类约定，一旦后端开始写就必须定死，否则每换一层框架都要重新适配 |
| **B. 数据模型与状态机未冻结** | 2、3、4、14 | 缺一张完整的实体与状态流转图，导致「补表 / 补字段 / 补态 / 文档失真」连锁发生 |
| **C. 平台与框架能力未先验** | 5、6、10、12、13、19、20 | 「以为支持、实际不支持」「以为生效、实际静默失效」——凡依赖他人实现，必须先写一个最小验证 |
| **D. UI 规范与临时原型滞后/返工** | 7、8、18 | Token 与原型策略是后置成本放大器；无后端支撑的假功能是演示可信度杀手 |
| **E. 验证、量化与收尾纪律** | 9、15、16 | 没有自动化验证脚本 / 度量方法错误 / 收尾盘点缺失 |

## 1. 立项前必须定死的事项（P0，写完签字）

### 1.1 需求边界

- [ ] **明确「不做清单」**，并承诺变更走流程：本项目初始定了「不做收藏/优惠券/积分/推送/在线阅读/退款」，后期因答辩需要加回「评价」——这本身不是错误，但应识别为**一次需求变更**：需要同步补表、补接口、补后台页、补 APP 页、改需求追溯矩阵。加一个需求 = 动五个地方。
- [ ] **单一需求源（SSOT）**：本项目同时存在 ima 知识库 SRS 与 `docs/需求规格说明书.md`，靠「冲突时以前者为准」兜底。**新项目只允许一份**，并用 `需求—实现追溯矩阵` 把每条需求映射到具体文件，取消需求时同步删除，避免「文档说有 / 代码没有」或反之。
- [ ] **写清演示与现实的分界**：模拟支付、假数据、占位图必须在立项时就写明哪些是模拟、切换真实需要什么（本项目把支付宝实现写完但如实标注「未与沙箱真实交互」，这是正确做法）。

### 1.2 数据模型（先冻结，再写代码）

- [ ] **一次性列全实体清单**，不要指望后期加表无痛。本项目初版 8 表漏了两类：
  - 审计类：`operation_log`（后台写操作留痕）；
  - 内容类：`review`（评价）。
  教训：**凡是「后台有人点」的系统，默认就要有操作日志表；凡是「UGC 内容」，默认就要独立表，不要塞进主表字段**。
- [ ] **每张表统一带**：`create_time`、`update_time`（自动填充）、软删除/状态字段、乐观字段按需。公共字段用 MyBatis-Plus 元对象处理器统一填，不要在业务代码里手写。
- [ ] **每个核心实体画状态机**，并作为验收依据。本项目订单状态到收尾才补齐闭环：`待支付 → 已支付 → 已发货 → 已完成` + `→ 已取消`，中间一度「已发货」是终态。
- [ ] **快照字段策略**：金额统一 `DECIMAL(10,2)`；订单冗余书名/封面/单价、收货地址快照；**明确哪些字段是快照（不可被后续编辑影响）**。
- [ ] **迁移脚本幂等**：用 `information_schema` 判断索引/列是否已存在再执行，允许重复跑（本项目 `migration_v2/v3/v4` 均按此写）。

### 1.3 前后端契约（写第一个接口之前）

- [ ] **统一返回体**：`{code, message, data, timestamp, requestId}`，HTTP 恒 200，成败只看 `body.code`。这条必须在写第一行代码前定；否则每接入一层新框架（本项目是 Spring Security，换了就得再写一层 401/403 转换器）都要重新适配一次。
- [ ] **错误码表落文档**：200/400/401/403/404/409/422/500 各自语义与示例文案。
- [ ] **分页结构统一**：`PageVO{list,total,pageNum,pageSize,pages}`，`pageSize` 上限保护**只写一处**（本项目抽 `BasePageQuery` 后才堵住「新查询 DTO 抄漏保护」）。
- [ ] **字段序列化约定（最容易被忽略，代价却最高）**：
  - 金额：`BigDecimal` 返回 `211.0` → 约定统一两位小数**字符串**或前端统一格式化，二选一，不要两边各写一半；
  - 时间：`LocalDateTime` 默认输出 `2026-10-16T10:48:07.825062` → 约定统一 `yyyy-MM-dd HH:mm:ss`；
  - **null 语义**：「无评价」返回 `null` 而非 `0`（0 分和暂无评分是两件事）。
- [ ] **VO 不含敏感字段**（password / salt），从第一天起，不做「先返回以后再删」。
- [ ] **列表接口必须返回前端渲染所需的全部字段**。判断标准：写页面时若需要为了渲染再发一次请求，就是后端字段不全（本项目订单列表缺 `items` 就是典型）。
- [ ] **前端→后端的错误三分类**：网络失败（拿不到响应）/ 业务失败（`code != 200`）/ 结构异常。各自的处理话术写死在 request 层。

### 1.4 技术与环境

- [ ] **第三方依赖分级**：必须（MySQL）/ 可降级（Redis）/ 可选（MinIO）。**可降级项必须有降级路径并有实测证据**——本项目杀掉 Redis 后所有接口仍 200 且数据正确，这一点值得保留为标配。
- [ ] **演示环境默认零依赖**：存储默认 `local`、支付默认 `mock`，需要展示高级能力时再切开关。
- [ ] **本机环境变量命名加项目前缀**，避免被运行环境注入的同名变量命中（本项目 `SERVER__PORT` → `server.port`）。
- [ ] **锁定依赖版本并核对该版本 API**，不要用较新版本的记忆写代码（MyBatis-Plus 3.5.7 是 `selectBatchIds`，3.5.9+ 才是 `selectByIds`）。

## 2. 开发过程必须遵守的约束

### P0（不做就会返工）

1. **平台差异先查表再写代码**。本项目 `<picker mode="region">` 在 App/H5 端明确不支持，官方推荐自行填充数据——一周后才发现。规则：**用到任何一个「看起来很方便」的官方组件前，先看文档的平台支持矩阵，App 端不支持就立刻换方案**。
2. **结构性 UI 改造要先列连锁影响清单**。移除原生 tabBar → `switchTab` 全失效 / 固定底栏互相遮挡 / 原生下拉刷新盖住自绘导航。规则：**凡改动导航模型、布局模式（fixed / custom 导航），先全局搜索相关 API 与定位类，列出受影响文件清单再动手**。
3. **没有后端支撑的假功能一律不做**。本项目的「客服中心」最终变成硬编码弹窗，演示时一眼看穿。规则：**功能必须有对应接口，接口不存在就砍需求，不做壳**。
4. **面向用户文案禁止出现技术话术**。「请确认 config.js 的 IP 正确」→「网络连接失败，请检查网络后重试」。排查信息只进 `console.error`。
5. **每个能力的验收脚本与代码同时提交**。本项目 258 项断言全绿的 `tools/verify_*.py`，是答辩当天唯一敢现场演示的底气。**没有脚本的能力 = 没有验证过的能力**。
6. **早于 Controller 抛出的异常必须单独处理**。`MaxUploadSizeExceededException`（参数解析阶段）不处理会落到兜底变成 500「服务器繁忙」。规则：**上线前把所有 500 都当作缺陷排查一遍**。

### P1（规范执行即可省下返工）

7. **禁止 N+1**：列表里要显示关联信息，一律「一次批量 IN + Map 回填」。本项目在分类名、订单明细、评分聚合、用户订单统计四处都按此写，无一踩坑。
8. **金额与时间的一致性规则只能有一处实现**。服务端负责算准（口径写进注释：销售额只含哪些状态），前端只在渲染层格式化，不在计算层重复实现金额逻辑；一旦前后端都在算，口径漂移只是时间问题。
9. **缓存策略按收益决定，且必须验证配置真的生效**。本项目两条硬经验：
   - 「写失效」优于「双写」：写库成功、写缓存失败会让用户看到错误的购物车数量；
   - **包装框架对象会改变其生命周期语义**：把 `RedisCacheManager` 包进自定义 `CacheManager` 后，它不再是 Bean，`initializeCaches()` 不执行，per-cache TTL 被静默忽略（5 分钟配成了 30 分钟）。规则：**包装第三方 Bean 之后，写一个断言把它的配置实测出来**（如 `TTL key` 必须等于 300）。
10. **管理端「菜单手写」必须有同步 Checklist**：新增页面 = 改 `router` + 改 `layout` 菜单 + 改 Knife4j 分组 + 改需求追溯矩阵。四处缺一就会出现「页面存在但没人找得到」。
11. **文档验收用「计数」而非「能打开」**。Knife4j 分组漏 `/api/review/**` 时文档照样能开，只是少了 5 个接口。规则：**每次交付核对「分组接口数 == 代码里统计的接口数」**。
12. **UI Token 从第一个页面起就用**。色值/字号/圆角/间距集中在 `uni.scss`，页面禁止硬编码。本项目把 14 个页面清一遍硬编码的代价，远大于一开始就用变量。
13. **Mock 数据必须一眼可辨 + 单一入口**。本项目 mock 图书主键从 10001 起配 `isMockId()` 判定，封面统一走 `cover.js`。规则：**Mock 只允许通过一个模块进入业务代码，且要写明是否会在交付前清退**。
14. **真机才是验收标准，模拟器与静态检查都不算**。CSS 图形、自绘导航层级、原生弹层、`@error` 是否触发，这四类只有在真机上才暴露。

### P2（锦上添花但成本很低）

15. **性能量化先定方法学**：多次采样取 **min**，冷调用前删缓存强制回源。用「首次 vs 中位」测到的是 JIT 预热，本项目据此一度得出「缓存负提升」的错误结论。
16. **跨页面通信谁注册谁注销**：`uni.$off(name)` 不带回调会移除全局所有同名监听，只能由注册方 `$off(name, handler)`。
17. **每日收尾生成开发日志**：进度 / 问题与根因 / 解决方法 / 待办 / 待确认决策点。本项目的日志在复盘时是唯一可信素材。
18. **收尾时必须做一次交付物盘点**（功能完成度 ≠ 交付完成度）。本项目功能 90% 时，APK 未打出、论文为 0、文档失真、AlipaySigner 未被调用。

## 3. 交付验收前自检清单（按顺序打勾）

### A. 契约与接口（最高优先级）

- [ ] 全量接口返回体一致；业务失败时 HTTP 恒为 200、`body.code` 正确
- [ ] 401 场景：前端确实清 token 并跳登录；403 场景：越权访问被拒
- [ ] 退出登录在服务端生效：登出后原令牌立即 401，且登出接口幂等（重复登出、无令牌、非法令牌都返回成功）
- [ ] 令牌有效期经过收敛判断（无「永久令牌」；缺 `exp` 的令牌被拒绝；有效期上限有校验）
- [ ] 错误码表与代码一致；**没有任何一处漏抓的 500**
- [ ] 鉴权按角色分别数据源（本项目踩过 admin 令牌查 user 表导致后台恒 401）
- [ ] 分页上限保护在所有列表接口生效（传 `pageSize=99999` 应被截断）
- [ ] 文档接口数 == 代码接口数；分组无遗漏
- [ ] VO 中不含 password / salt 等敏感字段

### B. 数据一致性与状态机

- [ ] 核心状态机全链路可走通并有对照数据（本项目：下单 → 支付 → 发货 → 收货 → 评价）
- [ ] 防超卖条件更新生效；重复操作幂等（重复支付/重复发货/重复取消均被拒，且副作用不重复发生）
- [ ] 取消订单能正确回滚库存与销量；超时任务与管理端手动触发结果一致
- [ ] 快照字段在源数据变更后仍正确（改价/下架/改地址后查历史订单）
- [ ] 演示数据可一键重置：`seed.sql` / `mock_dataset.sql` + 变更前的备份文件已留存

### C. 真机与环境

- [ ] 目标真机跑通主链路（不是为了 Demo 的分支路径）
- [ ] 所有需要下拉刷新的页面用 `scroll-view refresher`，不用页面级下拉
- [ ] 自绘导航 / 固定底栏 / 悬浮结算栏层级无遮挡
- [ ] Android 9+ 明文 HTTP 已放行（`usesCleartextTraffic`）
- [ ] 依赖降级实测：杀掉 Redis 后全部接口仍 200 且数据正确，且恢复后自动生效
- [ ] 打包前置项检查：`appid` 非空（本项目因 appid 为空，云打包任务根本未被受理）
- [ ] `manifest.json` / `pages.json` 是合法 JSON（严格格式，禁止注释）

### D. 文档与叙述

- [ ] 「待确认决策点」全部收敛，无悬而未决项
- [ ] 文档与代码一致：曾经写下的待办逐条复核是否仍然成立（本项目踩过「评价 UI 未落库」的过期待办）
- [ ] 测试报告数据全部来自实测；性能结论标注测量方法（本项目按此要求重写了缓存收益口径）
- [ ] 明确标注「模拟 / 未完成」的部分，不夸大（支付宝沙箱、占位封面）
- [ ] 每个能力项都能对应到一个可复跑的验证脚本

## 4. 决策复盘：哪些当初是对的，哪些本应规避

### 4.1 做对且应保留的决策

| 决策 | 为什么对 |
|---|---|
| **不用第三方 UI 库（uView）**，官方组件 + 自写 CSS | 零依赖、出问题时排查面最小；代价要接受的只是多写 CSS |
| **HBuilderX 标准结构而非 CLI** | 双击即开、真机运行与打包不依赖 npm 环境；毕设场景的风险最低路径 |
| **统一返回体 + requestId + 全局异常处理** | 前端只需一套错误处理分支；requestId 让日志与客户端报错可一一对应 |
| **HTTP 恒 200 + body.code**（虽然定得晚） | APP 端判断逻辑单一，真机最稳；代价是不符合 REST 语义，属明示取舍 |
| **密码用 BCrypt，且登录时惰性升级旧密文**、登录失败统一文案 | BCrypt 自带盐、代价可调，能扛住离线爆破；`PasswordUtil` 按密文格式自动选算法，老账号登录成功后就地重写，无需停机迁移、不用强制用户改密。统一文案防止账号枚举 |
| **改哈希算法时，别把「校验」写死成单一算法** | 若登录只认 BCrypt，存量 MD5 用户会全体登录失败。必须先"识别格式 → 分流校验 → 成功后再重写"，且重写失败只告警不阻断登录 |
| **别把「有验证码」当成「防住了暴力破解」** | 验证码只能挡无脑脚本；"取验证码 → OCR → 猜密码"完全绕得过去，人工慢速尝试更是毫无阻碍。必须另加**按账号维度的失败计数 + 临时锁定**。锁定检查要放在口令校验之前，否则锁定了还能继续试 |
| **限流维度选账号，别选 IP** | 公司/校园网出口 IP 被大量用户共用，按 IP 限流会把"一个人输错密码"变成"整栋楼登不上"。IP 维度只适合作为辅助，且阈值要放宽 |
| **防超卖用条件 UPDATE，不先查后改** | 由数据库保证原子性，并发下不会卖超；影响行数为 0 即回滚，不会出现「有订单没库存 / 有扣减没订单」 |
| **金额/地址/书名做快照** | 后续改价改名下架都不污染历史订单 |
| **存储抽象 + 本地默认，MinIO 可选** | 演示现场零依赖；`@PostConstruct` 失败只告警，避免「MinIO 没起 → 整个后端起不来」的连锁故障 |
| **支付做成抽象层 + 默认 mock 实现** | 答辩零依赖；真实渠道切换只改配置，不动业务代码 |
| **购物车缓存用写失效而非双写** | 一致性 > 命中率；用户看到自己购物车数量错误是不能妥协的场景 |
| **迁移脚本幂等** | 重复执行不报错、不重复建索引，可安全反复跑 |
| **「没有后端支撑的功能就砍掉」** | 功能真实性是演示可信度的基础 |
| **无状态 JWT 也要能「退出即失效」** | 只靠客户端删令牌，服务端在过期前仍认它 —— 令牌被复制走就能继续用。做法：签发时写入 `jti`，退出时把 `jti` 写入 Redis 黑名单（TTL = 令牌剩余有效期），过滤器逐请求校验。存储里只留「已失效」的少量条目，常态几乎为空，不需要把每个会话都存起来 |
| **令牌吊销要区分「收紧访问」与「放开访问」** | Redis 故障时，登录失败计数降级到本地内存（功能仍完整）；而黑名单必须**降级放行**并告警 —— 若一律拒绝，就把一次运维故障放大成全站用户被踢下线。同时黑名单降级窗口越小越好（本项目设 60 秒自动重试），因为期间其他实例吊销的令牌在本实例仍可用 |
| **登出接口必须幂等，且不能被吊销校验拦住** | 登出的目标是「让这枚令牌不可用」，本来就不可用时目标已达成，应返回成功。实践中踩到：过滤器命中黑名单就直接 401，导致重复点两次退出登录第二次报错。修法是把登出路径排除在吊销校验之外，而不是让前端去 catch |
| **别签发「永久令牌」** | `exp` 缺失的 JWT 永远不会过期，等于一把永久钥匙。校验时应显式要求 exp 存在（防御性校验，成本几乎为零），并在启动配置里给有效期设上限（本项目拒绝 > 720 小时） |
| **验证脚本的断言要写完再校准，别顺手写个「看起来对」的** | 本项目两次踩到：断言 `/api/book/list`（真实路径是 `/api/book/hot`）导致假失败；断言「带已失效令牌访问公开接口应 200」也写反了 —— 公开接口免登录不等于「接受任何凭证」，已吊销的凭证在任何接口上都应当被拒 |
| **验证脚本作为交付物的一部分** | 答辩现场一键复跑，比任何口头保证都有力 |
