## 1. 总体架构

系统采用**前后端分离 + 分层后端**架构，两端共用一套后端接口，通过路径前缀与角色区分能力边界：

```
┌────────────────────────── 表现层 ──────────────────────────┐
│ 用户端 APP（uni-app / Vue3）      管理端 Web（Vue3 + Vite）  │
│ 16 页面 + 8 组件                  9 页面 + Element Plus      │
└───────────────┬──────────────────────────┬─────────────────┘
                │ /api/**                  │ /api/admin/**
                └───────────┬──────────────┘
                            ▼
┌────────────────── 接口层（Controller） ──────────────────┐
│ 统一返回体 / 参数校验 / 鉴权入口 / Knife4j 文档            │
└───────────────────────────┬─────────────────────────────┘
                            ▼
┌────────────────── 业务层（Service） ────────────────────┐
│ 领域规则 / 事务边界 / 缓存注解 / AOP 操作日志             │
└───────────────────────────┬─────────────────────────────┘
                            ▼
┌────────────────── 数据访问层（Mapper / MyBatis-Plus） ───┐
└───────────┬───────────────────────────────┬─────────────┘
            ▼                               ▼
      MySQL 8（主存储）          Redis（缓存）/ MinIO（对象存储）
```

设计要点：**层间单向依赖**，Controller 不做业务判断，Service 不感知 HTTP；对象存储抽象为接口，本地磁盘与 MinIO 两种实现可切换。

## 2. 技术选型与理由

| 层次 | 选型 | 理由 |
| --- | --- | --- |
| 移动端 | uni-app（Vue3），HBuilderX 标准结构 | 一套代码产出 Android APK；官方组件 + 自写 CSS，避免第三方 UI 库带来的体积与兼容风险 |
| Web 端 | Vue3 + Vite + Element Plus | 组件齐全、上手快，hash 路由便于静态部署 |
| 后端框架 | Spring Boot 3.2.5 | 生态成熟、配置收敛，便于快速构建 RESTful 服务 |
| ORM | MyBatis-Plus 3.5.7 | 分页插件与条件构造器显著降低样板 SQL |
| 安全 | Spring Security + JWT(java-jwt 4.4.0) | 无状态鉴权，适配前后端分离；方法级 `@PreAuthorize` 做双保险 |
| 缓存 | Redis | 热点读加速；配熔断与降级，Redis 故障不阻断主流程 |
| 存储 | MinIO / 本地磁盘（可切换） | 演示环境免依赖，生产可平滑切至对象存储 |
| 文档 | Knife4j 4.5.0 | 接口文档随代码生成，避免文档与实现脱节 |

## 4. 关键设计决策

| 决策 | 说明与理由 |
| --- | --- |
| HTTP 状态码恒为 200 | 业务成败只看响应体 `code`。避免移动端把网络层错误与业务错误混为一谈，也便于统一拦截处理 |
| 统一返回体 | `{code, message, data, timestamp, requestId}`，`requestId` 贯穿日志，便于排障 |
| JWT 按角色分别查表 | 令牌携带 role，过滤器按 role 分别查 admin / user 表；查错表会恒定 401，是实践中踩过的坑 |
| 401/403 转统一返回体 | `RestAuthExceptionHandler` 将 Spring Security 的默认响应改写为统一结构 |
| 缓存 + 熔断降级 | Cache-Aside 写失效；`CacheCircuitBreaker` 在 Redis 连续失败后短时跳过缓存，保证可用性 |
| 对象存储抽象 | `FileStorageService` 双实现，默认 local，`STORAGE_TYPE=minio` 切换 |
| 支付回调返回 `void` | 直接写 `HttpServletResponse`，异常一律回文本 `failure`，避免 Spring 内容协商导致 406/500 |
| 定时任务关单 | `OrderTimeoutTask` 扫描超时未支付订单并关闭，释放库存 |
| 操作日志 AOP | `@OpLog` 注解 + 切面结构化落库，参数脱敏、超长截断 |

## 5. 接口设计

### 5.1 统一响应与错误码

| code | 含义 | 典型场景 |
| --- | --- | --- |
| 200 | 成功 | — |
| 400 | 参数有误 | 必填缺失、格式错误 |
| 401 | 未登录/过期 | 令牌缺失、过期、账号被禁用 |
| 403 | 无权限 | 普通用户访问 `/api/admin/**` |
| 404 | 数据不存在 | 资源 ID 不存在 |
| 409 | 数据冲突 | 手机号已注册、分类名重复、图书同名同作者 |
| 422 | 业务规则不允许 | 库存不足、订单状态不合法、重复评价 |
| 500 | 服务器异常 | 对外仅暴露通用文案 + `requestId` |

## 6. 前端设计

### 6.1 用户端 APP

- **页面组织**：16 个页面分 8 个业务域（首页、分类、图书、购物车、订单、地址、评价、我的/登录）；8 个公共组件复用（nav-bar、tab-bar、book-card、floor-title、channel-tabs、entry-grid、home-banner、state-view）。
- **自绘 tabBar**：放弃 `pages.json` 原生 tabBar，改为自绘组件。动因是原生角标无法随购物车实时联动；代价是 `uni.switchTab` 失效，tab 级跳转一律 `redirectTo`。
- **状态与存储**：令牌、用户信息存本地；未登录购物车落本机，登录后合并。
- **请求层**：统一封装 `common/request.js`，处理基址、令牌注入、401 清态跳登录；基址支持自动探测与手动配置。
- **UI 规范**：色值/字号全部 token 化于 `uni.scss`，页面禁止硬编码；触控区 ≥88rpx，正文 ≥26rpx。

### 6.2 管理端 Web

- hash 路由 + 路由守卫；`axios` 拦截器统一处理业务码与 401。
- 后端地址可运行时切换（`localStorage` + `setRequestBaseUrl`），避免重启 dev server。

## 7. 非功能设计

| 维度 | 设计 |
| --- | --- |
| 性能 | 热点读缓存（图书详情实测耗时降低约 36%）；热门榜用 `LIMIT` 下推而非全量截断；价格排序追加 id 次要键保证分页稳定 |
| 安全 | 密码加盐 MD5；JWT 无状态鉴权 + 方法级角色校验；越权返回 403；资源归属二次校验 |
| 可靠性 | Redis 熔断降级；支付回调异常一律返回 `failure` 文本，避免内容协商异常 |
| 可观测性 | `requestId` 贯穿、AOP 操作日志、Knife4j 接口文档 |
| 可移植性 | 对象存储可切换、后端地址可配置、数据库脚本按迁移版本管理 |
