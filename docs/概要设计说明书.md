## 1. 总体架构

系统采用**前后端分离 + 分层后端**架构，两端共用一套后端接口，通过路径前缀与角色区分能力边界：

```
┌────────────────────────── 表现层 ──────────────────────────┐
│ 用户端 APP（uni-app / Vue3）      管理端 Web（Vue3 + Vite）  │
│ 16 页面 + 8 组件                  9 页面 + Element Plus      │
└───────────────┬──────────────────────────┬─────────────────┘
                │ /api/**                  │ /api/admin/**
                └───────────┬──────────────┘
                            ▼
┌────────────────── 接口层（Controller） ──────────────────┐
│ 统一返回体 / 参数校验 / 鉴权入口 / Knife4j 文档            │
└───────────────────────────┬─────────────────────────────┘
                            ▼
┌────────────────── 业务层（Service） ────────────────────┐
│ 领域规则 / 事务边界 / 缓存注解 / AOP 操作日志             │
└───────────────────────────┬─────────────────────────────┘
                            ▼
┌────────────────── 数据访问层（Mapper / MyBatis-Plus） ───┐
└───────────┬───────────────────────────────┬─────────────┘
            ▼                               ▼
      MySQL 8（主存储）          Redis（缓存）/ MinIO（对象存储）
```

设计要点：**层间单向依赖**，Controller 不做业务判断，Service 不感知 HTTP；对象存储抽象为接口，本地磁盘与 MinIO 两种实现可切换。

## 2. 技术选型与理由

| 层次 | 选型 | 理由 |
| --- | --- | --- |
| 移动端 | uni-app（Vue3），HBuilderX 标准结构 | 一套代码产出 Android APK；官方组件 + 自写 CSS，避免第三方 UI 库带来的体积与兼容风险 |
| Web 端 | Vue3 + Vite + Element Plus | 组件齐全、上手快，hash 路由便于静态部署 |
| 后端框架 | Spring Boot 3.2.5 | 生态成熟、配置收敛，便于快速构建 RESTful 服务 |
| ORM | MyBatis-Plus 3.5.7 | 分页插件与条件构造器显著降低样板 SQL |
| 数据库迁移 | Flyway 9.22.3（`flyway-core` + `flyway-mysql`） | 结构变更版本化、可审计、可重放；启动即校验，避免「换台机器少建了几列」这类环境漂移。注：Flyway 8.2 起 MySQL 支持独立成模块，只引 `flyway-core` 会因找不到方言而启动失败 |
| 安全 | Spring Security + JWT(java-jwt 4.4.0) | 无状态鉴权，适配前后端分离；方法级 `@PreAuthorize` 做双保险 |
| 缓存 | Redis | 热点读加速；配熔断与降级，Redis 故障不阻断主流程 |
| 存储 | MinIO / 本地磁盘（可切换） | 演示环境免依赖，生产可平滑切至对象存储 |
| 文档 | Knife4j 4.5.0 | 接口文档随代码生成，避免文档与实现脱节 |

## 3. 后端模块划分

```
cn.edu.bookstore
├── common       统一返回 Result、ErrorCode、BusinessException、RequestContext
│   ├── web      JwtAuthenticationFilter、RestAuthExceptionHandler、LoginUserHolder

│   ├── storage  FileStorageService → Local / Minio 两套实现
│   ├── pay      AlipaySigner（支付签名工具，模拟支付场景下的扩展预留）
│   ├── lock     RedisLock
│   ├── security LoginAttemptGuard（登录失败锁定）、TokenRevocationService（令牌吊销）
│   ├── util     JwtUtil（签发/校验，载荷含 jti）、PasswordUtil
│   ├── observability BusinessMetrics（业务埋点）、BookstoreInfoContributor、CacheHealthIndicator
│   └── log      OpLog 注解 + AOP 落库、JsonLogEncoder（结构化日志编码器）
├── config       SecurityConfig、MybatisPlusConfig、SchedulingConfig、WebConfig
├── controller   25 个 Controller（用户端 13 + 管理端 12）

├── entity       与表一一对应的实体
├── model/dto    入参
└── model/vo     出参
```

本轮（W1）新增的 5 个业务模块，落位方式与既有模块完全一致（`entity` / `mapper` / `service`+`impl` / `controller` / `dto` / `vo` 各一份），没有引入新的分层概念：

| 模块 | 职责 | 关键约束 |
| --- | --- | --- |
| `booklist` 书单 | 用户自建书单与条目增删，公开/私密两态，公开书单进广场 | 每人最多 50 个书单、单书单最多 200 本；`book_count` 冗余计数只在本模块维护；私密书单对非创建者返回 **403**（而非 404 —— 自增 ID 藏不住存在性，返回「不存在」只会误导创建者）；删除时先清条目再删主表；列表页的创建者昵称与封面走批量装配，不做 N+1 查询 |
| `browsehistory` 浏览历史 | 记录 / 分页 / 合并 / 单项与全量删除 | 每人每书仅一条（唯一键），重复浏览只推进 `view_time`；每人最多保留 100 条，超出部分按时间淘汰最旧的；`merge` 的返回值只统计**真正新插入**的行，不把「刷新已有记录的时间」算进去（前端拿它提示「已同步 N 条」，口径不一致就会报出与列表增量对不上的数字） |
| `banner` 轮播图 | 首页轮播位内容与启停 | 只返回 `status=1` 的条目，按 `sort` 升序、`id` 升序（排序号相同时结果稳定）；整个可见列表走 `@Cacheable(value="banner", key="'visible'")`，写操作 `@CacheEvict(allEntries=true)` 且经 `TransactionAwareCacheManager` 延后到事务提交后才清 —— 回滚不清、并发的旧值回填窗口也一并消掉 |
| `freight` 运费 | 运费门槛与费率的读取与试算 | 三个配置键 `freight.enabled` / `freight.free-threshold` / `freight.base-fee` 存 `sys_config`，缺失时回落到 `AppProperties`（yml 只做兜底）；`sys_config` **刻意不加缓存** —— 后台改完下一单立刻生效，比省一次小表查询重要；金额一律 `BigDecimal`，门槛判断 `compareTo >= 0`（达到即免运），门槛 `<=0` 显式判「关闭门槛」而非依赖「任何金额都 ≥ 0」的巧合 |
| `stocknotice` 到货提醒 | 无库存图书的订阅、我的订阅、管理端聚合与批量标记 | 仅在「上架且 `stock=0`」时可订阅（有货直接下单、下架补货也买不到）；每人每书一条（唯一键），取消后重新订阅**复用原行**而非删了重插，否则反复订阅会撑出多行、唯一键形同虚设；补货后管理端可一键把该书待通知全部置为已通知 |

订单模块本轮另有增强（未新增控制器）：`orders` 增加 `freight_amount` / `ship_time` / `finish_time` 三列，订单详情据此返回时间线节点（下单 → 支付 → 发货 → 完成），结算预览接口返回小计 / 运费 / 应付三段金额。

## 4. 关键设计决策

| 决策 | 说明与理由 |
| --- | --- |
| HTTP 状态码恒为 200 | 业务成败只看响应体 `code`。避免移动端把网络层错误与业务错误混为一谈，也便于统一拦截处理 |
| 统一返回体 | `{code, message, data, timestamp, requestId}`，`requestId` 贯穿日志，便于排障 |
| JWT 按角色分别查表 | 令牌携带 role，过滤器按 role 分别查 admin / user 表；查错表会恒定 401，是实践中踩过的坑 |
| 401/403 转统一返回体 | `RestAuthExceptionHandler` 将 Spring Security 的默认响应改写为统一结构 |
| 令牌可吊销 | 令牌携带 `jti`，退出登录时写入 Redis 黑名单（TTL = 令牌剩余有效期），过滤器逐请求校验。纯无状态 JWT 无法「退出即失效」，这是补齐该短板的最小改造 |
| 令牌有效期收敛 | 由 72 小时收敛为 24 小时（生产 12 小时）。JWT 过期前无法远程作废，有效期越长风险窗口越大；退出登录已可吊销后，缩短有效期不再带来额外重登困扰 |
| 缓存 + 熔断降级 | Cache-Aside 写失效；`CacheCircuitBreaker` 在 Redis 连续失败后短时跳过缓存，保证可用性 |
| 缓存清理时机 | 在 `CacheConfig` 里把缓存管理器**再包一层** `TransactionAwareCacheManager`：写操作（`evict`/`clear`/`put`）注册到事务同步，只在 `afterCommit()` 真正落到 Redis，事务回滚则一律不动。原形态「方法返回后、事务提交前」清空缓存，存在「缓存已清 → 并发读回填旧值 → 事务提交 → 脏值存活到 TTL 到期」的不一致窗口。零业务改动（不碰任何 `@CacheEvict` 注解）、可开关（`bookstore.cache.evict-after-commit`）、可回退、可做对照实验 |
| 为何不用 Spring 自带的 `TransactionAwareCacheManagerProxy` | 其 `afterCommit` 回调**不吞异常**：Redis 若在提交后恰好失败，异常会抛给「业务其实已经提交成功」的调用方；而且此时已脱离缓存切面，`CacheErrorHandler` 兜不住。自实现的版本在 `afterCommit` 里 try/catch 只记 warn —— 缓存是纯加速项，清理失败不该把一次成功的业务写变成失败 |
| 缓存包装层顺序 | 外层 `TransactionAwareCacheManager`（管「**什么时候**清」）→ 内层 `ResilientCacheManager` + `CacheCircuitBreaker`（管「**能不能**清」）。顺序是有意的：提交后真正落 Redis 时才做熔断判断，依据是那一刻的状态而非事务开始时的状态 |
| Flyway 纳管迁移 | `db/migration/V*.sql` 为结构权威来源，服务启动即自动迁移。已有库用 `baseline-on-migrate` + `baseline-version` 打基线（跳过历史脚本、不动数据），全新库从 V1 顺序跑完 —— 换台机器只需「建空库 + 启动服务」。配套 `db/schema.sql` 作**结构快照**保留手工建库路径，并由 `verify_flyway_migration.py` 逐表/逐列/逐索引比对快照与实际库，防止两条路径长期漂移 |
| 对象存储抽象 | `FileStorageService` 双实现，默认 local，`STORAGE_TYPE=minio` 切换 |
| 支付回调返回 `void` | 直接写 `HttpServletResponse`，异常一律回文本 `failure`，避免 Spring 内容协商导致 406/500 |
| 定时任务关单 | `OrderTimeoutTask` 扫描超时未支付订单并关闭，释放库存 |
| 操作日志 AOP | `@OpLog` 注解 + 切面结构化落库，参数脱敏、超长截断 |
| 运维端点分权 | actuator 仅放行 `health`/`info`（探测与部署自证），其余 `/actuator/**` 需 ADMIN 角色；生产只暴露 `health`。放行清单显式枚举而不写 `/actuator/**`，避免「图省事」把 `env`/`heapdump` 一并放开 |
| 业务埋点只做 Counter | 复用 Micrometer，指标标签只用低基数枚举（scope/result/role），**绝不把手机号、订单号写入标签** —— 标签基数爆炸会拖垮指标后端；埋点开关 `bookstore.observability.metrics-enabled` 可一键关闭 |
| 缓存健康恒判 UP | 自定义 `CacheHealthIndicator` 在缓存熔断时仍返回 UP，只把 `degraded=true` 放进明细。理由：熔断时业务已降级走数据库、对外仍可用，若判 DOWN 会被负载均衡误摘实例，把小故障放大成全站不可用 |
| 日志形态按 profile 分流 | `logback-spring.xml` 用 `<springProfile>` 分流：非 prod 输出人读文本（含 `[requestId]`），prod 输出行式 JSON（便于采集端按字段索引）；自写 `JsonLogEncoder`（Jackson），不引入 logstash 依赖 |
| `requestId` 落到 MDC | 请求入口写入 MDC，日志编码器从 MDC 取 `requestId`；因此框架组件（连接池、校验器等）的日志同样带链路 ID |

## 5. 接口设计

### 5.1 统一响应与错误码

| code | 含义 | 典型场景 |
| --- | --- | --- |
| 200 | 成功 | — |
| 400 | 参数有误 | 必填缺失、格式错误 |
| 401 | 未登录/过期 | 令牌缺失、过期、已登出（命中吊销黑名单）、账号被禁用 |
| 403 | 无权限 | 普通用户访问 `/api/admin/**` |
| 404 | 数据不存在 | 资源 ID 不存在 |
| 409 | 数据冲突 | 手机号已注册、分类名重复、图书同名同作者 |
| 422 | 业务规则不允许 | 库存不足、订单状态不合法、重复评价 |
| 500 | 服务器异常 | 对外仅暴露通用文案 + `requestId` |

## 6. 前端设计

### 6.1 用户端 APP

- **页面组织**：16 个页面分 8 个业务域（首页、分类、图书、购物车、订单、地址、评价、我的/登录）；8 个公共组件复用（nav-bar、tab-bar、book-card、floor-title、channel-tabs、entry-grid、home-banner、state-view）。
- **自绘 tabBar**：放弃 `pages.json` 原生 tabBar，改为自绘组件。动因是原生角标无法随购物车实时联动；代价是 `uni.switchTab` 失效，tab 级跳转一律 `redirectTo`。
- **状态与存储**：令牌、用户信息存本地；未登录购物车落本机，登录后合并。
- **请求层**：统一封装 `common/request.js`，处理基址、令牌注入、401 清态跳登录；基址支持自动探测与手动配置。
- **UI 规范**：色值/字号全部 token 化于 `uni.scss`，页面禁止硬编码；触控区 ≥88rpx，正文 ≥26rpx。

### 6.2 管理端 Web

- hash 路由 + 路由守卫；`axios` 拦截器统一处理业务码与 401。
- 后端地址可运行时切换（`localStorage` + `setRequestBaseUrl`），避免重启 dev server。

## 7. 非功能设计

| 维度 | 设计 |
| --- | --- |
| 性能 | 热点读缓存（图书详情实测耗时降低约 36%）；热门榜用 `LIMIT` 下推而非全量截断；价格排序追加 id 次要键保证分页稳定 |
| 安全 | 密码以 BCrypt 慢哈希存储（历史 MD5 密文登录时透明升级）；JWT 无状态鉴权 + 方法级角色校验；令牌有效期收敛至 24 小时（生产 12 小时）且退出登录在服务端吊销（jti 黑名单，Redis 故障时降级为仅本实例生效）；越权返回 403；资源归属二次校验；登录失败达阈值临时锁定账号（Redis 计数，按账号域隔离） |
| 可靠性 | Redis 熔断降级；支付回调异常一律返回 `failure` 文本，避免内容协商异常；缓存熔断不误报实例失活（健康检查恒 UP）；缓存清理失败不影响已提交的业务（提交后清理异常仅告警，`D-06`） |
| 一致性 | 缓存清理与事务提交对齐（`afterCommit` 才清、回滚不清），消除「清空后被并发回填旧值」的窗口；购物车走 Cache-Aside 写失效 |
| 可观测性 | 三支柱齐备：**指标**（Micrometer + actuator `/metrics`，框架自动指标 + 六项业务计数器）；**日志**（`requestId` 贯穿 MDC，prod 输出行式 JSON，local 输出人读文本，文件按 20MB/15 天/1GB 滚动归档）；**健康检查**（`/actuator/health` 聚合 db/redis/缓存组件，供负载均衡探测）。另有 AOP 操作日志落库与 Knife4j 接口文档 |
| 可移植性 | 对象存储可切换、后端地址可配置、数据库结构由 Flyway 版本化自动迁移（已有库可打基线接入，全新库一条命令建好） |
