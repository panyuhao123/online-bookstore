## 4. 关键技术论述要点（可直接展开成小节）

1. **无状态鉴权与双表查询**：JWT 携带角色，过滤器按角色分别查询 admin / user 表；若统一按一张表查，会导致另一类用户恒定 401。这是实现中的实际坑点，可写成"问题—分析—解决"。
2. **防超卖**：`UPDATE book SET stock = stock - n WHERE id = ? AND stock >= n`，以影响行数判定成败，避免"先查后写"的竞态。
3. **缓存与降级**：Cache-Aside + 写失效；Redis 连续失败后熔断直接回源，保证缓存故障不影响可用性。
3.1 **缓存失效与事务提交的时序对齐**（一个可写成"发现—分析—取舍—验证"完整链条的点）：
   默认 `@CacheEvict` 在「方法返回后、事务提交前」执行，于是存在这样的窗口 —— 缓存已被清空、事务尚未提交，
   此刻的并发读会把**旧值**重新填进缓存，等事务提交后这个脏值会一直存活到 TTL 到期。
   解法不是去改那 20 多处 `@CacheEvict` 注解，而是在 `CacheConfig` 里把 `CacheManager` **再包一层**：
   写操作注册到 `TransactionSynchronization`，只在 `afterCommit()` 才真正落到 Redis，回滚则一律不动。
   取舍点有两个：① **为什么不用 Spring 自带的 `TransactionAwareCacheManagerProxy`** —— 它的 `afterCommit`
   回调不吞异常，Redis 若在提交后恰好失败，异常会抛给"业务其实已经提交成功"的调用方，且此时已脱离缓存切面、
   `CacheErrorHandler` 兜不住；自实现版本只记 warn，因为缓存是纯加速项，清理失败不该把一次成功的业务写变成失败。
   ② **包装层的顺序** —— 外层管"什么时候清"，内层（熔断/降级）管"能不能清"，使熔断判断依据的是提交那一刻的状态。
   验证分工同样值得写：微秒级时序由 11 项单元测试精确控制「提交前/提交后/回滚」三个时点，
   端到端脚本只验行为、形态与不回归；并用一个关掉开关的对照实例证明可回退。
4. **定时任务幂等**：超时关单重复触发不重复回补库存（测试中有专项用例）。
5. **评价防刷与治理**：唯一键 `(user_id, book_id, order_id)` 从数据层保证"买过才能评、同单同书只评一次"；违规评价采用隐藏而非删除，保留追溯能力。
6. **支付回调的健壮性**：回调接口返回 `void` 并直接写响应，异常一律回复文本 `failure`，避免 Spring 内容协商产生 406/500 造成网关无限重推。
7. **前端自绘 tabBar 的取舍**：放弃原生 tabBar 换取购物车角标实时联动；代价是 `uni.switchTab` 失效，需改用 `redirectTo` 并自行控制页面栈。
8. **对象存储抽象**：`FileStorageService` 接口 + 本地/MinIO 双实现，演示环境零依赖，生产可平滑切换。
9. **无状态会话的可吊销改造**：JWT 的"退出登录"原本只在客户端删令牌，服务端在过期前仍认它 ——
   令牌一旦被复制走（抓包、共享设备、日志泄露）就无法收回。改造方式是签发时写入唯一编号 `jti`，
   退出时把 `jti` 写入 Redis 黑名单（TTL = 令牌剩余有效期），认证过滤器逐请求校验。
   与"服务端存会话表"相比的取舍：会话表能即时吊销，但每个请求都要访问共享存储、Redis 故障即全站无法登录；
   黑名单只存"已失效"的少量条目（常态几乎为空），Redis 故障时损失的是吊销能力而非可用性。
   该设计可直接写成"安全性改进"小节，配套 38 项端到端断言。
10. **可观测性三支柱的落地**：以 Spring Boot Actuator + Micrometer 为骨架，把"指标、日志、健康检查"三根支柱一次补齐。
    指标层复用框架自带的 `http.server.requests`（接口调用量与耗时分布），只自行补齐框架看不到的业务量：登录成败
    （按 `scope=user|admin`、`result=success|failure|locked` 分桶）、令牌吊销、下单与支付。**标签全部使用低基数枚举，
    不把手机号或订单号写进标签** —— 这是埋点最容易被忽略的陷阱，高基数标签会为每个取值创建独立时间序列，直接压垮指标后端。
    日志层用 `<springProfile>` 按环境分流：开发环境输出人读文本，生产环境输出行式 JSON 供采集端按字段索引；
    `requestId` 写入 MDC 后由编码器统一读取，因此连接池、参数校验器等**框架组件**的日志也自动带上链路 ID。
    健康检查层除框架自带的数据库/Redis 指示器外，另加一个缓存健康指示器，其设计取舍值得单独论述：
    **缓存熔断时健康检查仍返回 UP**，只把 `degraded=true` 放进明细 —— 因为此时业务已降级走数据库、对外仍然可用，
    若判 DOWN 会被负载均衡摘掉本该继续服务的实例，把一次缓存抖动放大成全站不可用。
    该节可配合"反向断言"的方法论展开：验证时不仅断言"指标能读到"，而是"操作前记录计数 → 触发一次 → 断言恰好 +1"，
    以及"未开放端点对管理员也必须 404"，后者才是最小暴露原则成立的真正证据。

## 5. 创新点建议（择 2~3 条）

1. **面向演示与真实性的数据工程**：以脚本化方式抓取并三重校验真实图书封面，配套核验脚本，避免演示数据失真。
2. **缓存韧性设计**：缓存层不是"可选装饰"，而是带熔断与降级的可用组件，故障可验证、可量化。
3. **评价治理模型**：以"订单绑定 + 唯一约束 + 隐藏优先"构建可信评价与可追溯治理的组合方案。
4. **端到端脚本化验证 + 一键质量门禁**：把需求点固化为可重复执行的断言脚本（端到端 414 项 + 单测 214 项），并用一条命令把「环境预检 → 自动起停后端 → 全部检查 → 汇总报告」串起来，使测试过程可复现、可回归；强调"反面断言"（未开放端点必须 404、信息端点不得含凭证）比"正面可用"更能暴露配置疏漏，以及**门禁必须区分"失败"与"覆盖不完整"**（否则环境抖动会被误判成代码缺陷，或覆盖不足伪装成绿灯）。
5. **可观测性的一体化设计**：把指标、日志、健康检查与既有的安全防护（端点分权、最小暴露、防泄露）放在同一设计框架下权衡，其中"缓存降级不判负健康检查"是一个典型的"避免把小故障放大成大故障"的取舍案例。

## 6. 答辩常见问题与回答要点

| 问题 | 回答要点 |
| --- | --- |
| 支付是真的吗？ | 是模拟支付：不接入真实渠道，重点验证订单状态机、回调处理与异常兜底；回调对伪造请求统一回复 `failure` |
| Redis 挂了系统还能用吗？ | 能。缓存层带熔断与降级，Redis 故障期间直接回源数据库，仅性能下降，功能不受影响 |
| 如何防止超卖？ | 条件更新 SQL + 事务；以影响行数判定成败，避免先查后写的竞态 |
| 评价能刷吗？ | 不能。评价必须与已完成订单绑定，唯一键约束同单同书只能评一次 |
| 为什么评价是隐藏而不是删除？ | 删除不可逆、无法追溯与申诉；隐藏同样能立即从前台与平均分中移除，且可恢复 |
| 缓存与数据库不一致怎么办？ | 采用 Cache-Aside，写操作失效缓存，且**清理动作注册到事务提交后执行**（回滚则不清），消除"缓存已清、事务未提交、并发读回填旧值"的窗口；仍允许提交后清理失败等极端情况下的短暂不一致（上限为缓存 TTL，且此时读到的仍是数据库新值或走降级路径），读多写少场景下代价可接受 |
| 密码为什么从 MD5 换成 BCrypt？ | MD5 是"快哈希"，加盐只能防彩虹表，挡不住 GPU 离线爆破。已升级为 BCrypt（自适应慢哈希，代价因子 10，盐内置于密文），BCrypt 密文恰好 60 字符、可原样存入既有 `password VARCHAR(64)`，无需改表；老账号在登录成功后由服务层就地重写，用户无感。这一段可直接写进"安全性改进"小节 |
| 为什么不做收藏、优惠券？ | 范围裁剪：优先保证购物主链路与评价治理的完整性；可在展望中列为后续迭代 |
| 光有验证码能挡住暴力破解吗？ | 挡不住。验证码只能拦住"无脑脚本"，攻击者完全可以脚本化地"取验证码 → OCR → 猜一个密码"，或者人工慢速尝试，这类请求在验证码视角下完全正常。真正有效的是**按账号维度的失败计数**：连续失败 5 次即锁定 15 分钟，把"无限次尝试"压成"每 15 分钟 5 次"，使口令穷举在时间维度上不可行。两点设计细节可直接写进论文：① 计数只按账号、不按 IP —— 公司/校园网出口 IP 常被大量用户共用，按 IP 限流会把一个人的输错变成整栋楼都登不上；② 不存在的账号同样计数，否则"不存在的账号永远不锁"本身就成了账号枚举的信号 |
| 计数为什么要过期？ | 计数窗口 30 分钟、锁定 15 分钟，都靠 Redis TTL 自动过期。若计数永久累积，正常用户几个月里零星输错几次也会被误锁；若不设锁定 TTL，一次误锁会永久锁死账号 |
| 用户退出登录后，那枚令牌还能用吗？ | 不能。退出时会把令牌编号（`jti`）写入 Redis 黑名单，之后这枚令牌在任何接口上都被拒绝（401「登录状态已失效」）。JWT 是无状态的，这是补齐"退出即失效"的最小改造：不需要把每个会话都存起来，只记录"已失效"的少量条目 |
| 黑名单会不会越积越多？ | 不会。键的 TTL 等于令牌的剩余有效期，令牌自然过期后黑名单条目随之消失。另外黑名单只覆盖"仍可能被使用"的时间段，过期令牌根本不需要入表 |
| Redis 挂了会不会把所有用户踢下线？ | 不会，这是刻意的取舍。缓存层熔断回源；令牌吊销则降级为"本实例内存生效 + 告警 + 60 秒后自动重试连接" —— 业务接口照常可用，只是故障窗口内别的实例上的已登出令牌可能仍被接受。反过来若选择"一律拒绝"，一次 Redis 故障就会放大成全站用户被踢下线 |
| 令牌有效期为什么从 72 小时改成 24 小时？ | JWT 在过期前无法被远程作废（除非命中黑名单），有效期越长，令牌泄露后的风险窗口越大。收敛到 24 小时（生产 12 小时）后，配合退出即吊销，既缩短了风险窗口，也不会带来额外的重登困扰。校验时还显式要求 `exp` 存在，避免出现"永久令牌" |
| APP 为什么不用原生 tabBar？ | 原生角标无法随购物车实时联动；自绘的代价是 `switchTab` 失效，已用 `redirectTo` 统一处理 |
| 换台电脑能跑起来吗？ | 可以：数据库脚本按版本管理，后端地址可在 APP 与后台运行时配置；依赖 Redis/MinIO 可降级 |
| 为什么要引入 actuator？会不会反而多开了一堆漏洞？ | 引入观测能力与"少开面"并不矛盾，关键是**分权 + 最小暴露**：只放行 `health`（负载均衡探测必需）与 `info`（部署自证，只报开关不报凭证），其余 `/actuator/**` 一律要求 ADMIN 角色；生产环境更只暴露 `health`。`env`、`beans`、`heapdump` 这些真正敏感的端点**压根不开放** —— 实测即使带 ADMIN 令牌访问也返回 404。也就是说安全性由"不暴露"保证，而不是仅靠"有权限" |
| 埋点会不会拖慢接口？ | 埋点只做内存中的计数器自增（Micrometer Counter），没有 I/O，开销可忽略；且提供了 `bookstore.observability.metrics-enabled` 开关，可以一键关闭后再对比验证。需要注意的是**别让标签基数失控** —— 标签取值数量决定时间序列数量，把订单号这种高基数字段写进标签才会真正拖垮监控系统，因此标签只用 `scope`/`result`/`role` 三个低基数枚举 |
| 健康检查为什么不把"缓存不可用"判为不健康？ | 因为此时业务并没有不可用。缓存熔断后请求会直接回源数据库，用户侧功能完全正常，只是变慢。若健康检查判 DOWN，负载均衡/容器编排会把本来还能服务的实例摘掉，一次 Redis 抖动就被放大成全站不可用。所以设计成恒 UP、把 `degraded=true` 写进明细，让运维能看到异常但不误摘实例 |
| 日志为什么要区分环境？ | 开发时人读文本最方便（含 `[requestId]` 便于本地排障）；生产环境要交给采集端（Filebeat/Fluent Bit）按字段索引与检索，行式 JSON 才是合适的形态。工程上有两个必须注意的细节：配置文件必须叫 `logback-spring.xml`（叫 `logback.xml` 时 `<springProfile>` 不生效），且一旦定义了它，`application.yml` 里的 `logging.pattern.*` 会被静默忽略（成为"死配置"）。结构化日志的第一要求是"一条 = 一行"：多行异常栈必须转义进单个字段，否则采集端会把它拆成多条残缺记录 |
| 怎么证明埋点真的接上了？ | 不能只断言"指标能读到"——配置错位时也可能恰好读到别的指标。做法是：先读一次计数 → 触发一次业务操作 → 再读，断言**恰好 +1**。本项目对登录失败/成功、管理员登录失败、令牌吊销、下单、支付六项计数器都做了这种"增量断言"，全部通过 |
| 你的测试有多少？怎么证明覆盖到位？ | 一条命令产出的门禁结果是：端到端 414 项 + 后端单测 192 项 + 管理端单测 22 项 + 前端静态 38 项 = **666 项通过、1 项已知预期失败**（`tools/run_all_checks.py`，133.9s）。但要说明**断言数量不等于覆盖质量**：端到端跑再多，也构造不出"库存恰好不足""条件更新影响 0 行""地址越权"这类分支，这些必须在 Service 单测里精确构造 —— 所以本轮特意把单测从 123 项补到 192 项，重点就是此前几乎空白的下单 / 支付 / 取消 / 购物车合并逻辑 |
| 测试会不会"假绿"？ | 有针对性设计：① 门禁对**解析不到汇总行**的情况报"异常"而不是算作 0 通过，避免脚本跑挂被当成零断言通过；② 测试完整性**靠比对测试文件数**判断，而不只看断言总数 —— 实测踩过一次：vitest 因写临时文件失败中断收集阶段，3 个测试文件只跑了 2 个，但汇总行依然显示 `0 failed`；③ 门禁把"测试失败"（影响退出码）与"覆盖不完整"（单独提示、不影响退出码）分成两种状态，避免环境抖动被误判成代码缺陷 |
| 为什么把回归做成一条命令？ | 此前跑完整回归要手工做五件事：起依赖、起后端、等就绪、逐个跑 9 个脚本、自己加总。手工步骤越多，越容易漏跑脚本或跑在错误实例上（例如忘记重启服务，新代码根本没被验证到）。固化成脚本后，这两类问题从"靠人记得"变成"结构上不可能发生" |

1. 接入真实支付渠道与退款、售后流程；
