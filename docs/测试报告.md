## 1. 测试目的与范围

验证系统是否达成需求规格中定义的功能与质量目标，重点覆盖：

1. 用户端核心链路：登录 → 浏览/搜索 → 购物车 → 下单 → 支付 → 收货 → 评价；
2. 管理端核心能力：图书/分类/订单/用户/评价管理与操作日志；
3. 非功能属性：鉴权与越权防护、参数校验与异常处理、缓存与降级、定时任务幂等、接口文档完整性；
4. 可观测性（批 5 新增）：健康检查、运行信息、指标端点及其鉴权边界、业务埋点计数、结构化日志。
5. 一致性与可部署性（批 6 新增）：缓存清理时机（事务提交后 / 回滚不清理）、数据库迁移由 Flyway 统一纳管并在全新空库上可一键建库。
6. 测试工程化（批 7 新增）：后端核心 Service 层单元测试补齐、管理端引入自动化测试、**一条命令跑完全部回归**。

### 2.1 一键回归（批 7 新增，质量门禁入口）

此前跑一次完整回归需要在终端手工做五件事：起 Redis / MinIO、起后端、等就绪、逐个跑 9 个脚本、自己把「通过 N 项」加起来。手工环节越多越容易漏跑脚本或跑在错误实例上。`tools/run_all_checks.py` 把这条链路固化成一条命令：

```bash
python tools/run_all_checks.py --with-unit --with-admin --with-frontend   # 质量门禁口径
python tools/run_all_checks.py                                            # 只跑端到端（自动起停服务）
python tools/run_all_checks.py --reuse-server --only=verify_capabilities  # 复用现有实例、只跑指定的几项
```

设计要点（均为实测踩坑后的选择）：

| 要点 | 做法与原因 |
| --- | --- |
| 就绪判据 | 轮询 `/api/category/list` 而**不是** `/actuator/health` —— 后者不查库、恒 200，会出现「端口已监听但数据库没连上」却判为就绪 |
| 服务生命周期 | 默认自己拉起并在收尾 `taskkill /F /T` 整棵进程树；跑单测前必须先停服，否则 `mvn test` 与 `spring-boot:run` 争用 `target/` |
| 汇总行解析 | 9 个脚本历史上格式不一，为每个格式写独立解析器；**解析不到会被标为「异常」而不是悄悄算 0 通过**，避免掩盖问题 |
| 颜色码 | 统一剥离 ANSI 转义序列后再解析 —— vitest 在管道下也照样上色，`Tests  22 passed` 被颜色码切开后正则整行失配 |
| 已知预期失败 | `check_app_sfc.cjs` 的 1 项失败（`common/config.js` 的 `#ifdef` 重复导出）在脚本中显式声明为「允许的预期失败」，汇总中标为 `通过*` |
| 「需留意」与「失败」分开 | 断言数字按实际跑到的如实统计；若检测到「管理端只跑了 2/3 个测试文件」这类**覆盖不完整**，单独列入「需留意」并**不影响退出码** —— 不把环境问题误判成代码问题，也不让不完整覆盖伪装成通过 |
| 报告落盘 | 每次运行写入 `tools/out/regression_<时间戳>.md`，含逐项结果、耗时与备注 |

## 4. 用例覆盖明细

### 4.1 基础能力与异常（66 项）

| 分组 | 关键用例 |
| --- | --- |
| 数据库连通与统一返回 | HTTP 恒 200；响应含 `code/message/data/timestamp/requestId`；用分类接口判定数据库连通（不用 `/health`） |
| 分页与筛选 | 分页参数生效；总页数正确；关键词命中且结果无脏数据；分类筛选正确；超大 `pageSize` 收敛为 50（防拖库） |
| 价格区间 | 区间筛选正确；仅传单边正确；区间写反自动交换；负数下限被忽略 |
| 权限控制 | 匿名访问受限资源返回 401；普通用户访问管理端返回 403；越权操作被拒 |
| 文件上传 | 上传接口可用，返回可访问地址 |
| 购物车合并 | 未登录本地数据合并到服务端，合并后不重复 |
| 订单与库存 | 下单扣减库存；取消订单回补库存；重复触发回补幂等 |
| 全局异常处理 | 参数校验失败返回 400；业务冲突返回 409；内部异常不暴露堆栈 |

| 分组 | 关键用例 |

### 4.4 会话可吊销（38 项）

| 分组 | 关键用例 |
| --- | --- |
| 令牌签发 | 登录返回的 JWT 载荷含唯一 `jti`；同一账号两次登录 `jti` 不同；令牌携带 `exp`（无永久令牌） |
| 吊销生效 | 退出登录后，原令牌访问 `/api/user/info`、`/api/cart/list` 等受保护接口均返回 401「登录状态已失效，请重新登录」 |
| 跨端域隔离 | 用户令牌被吊销不影响管理员令牌，反之亦然；黑名单值分别为 `user:<id>` / `admin:<id>` |
| 幂等与鲁棒 | 同一枚令牌连续登出两次均返回成功（登出路径不参与吊销校验）；撤销不存在的令牌不报错 |
| 公网浏览不受影响 | 不带令牌访问 `/api/book/hot` 等公开接口返回 200 |
| 有效期收敛 | 黑名单键 TTL ≈ 令牌剩余有效期（实测 86398/86399 秒）；重新登录签发新令牌可用，旧令牌不复活 |

### 4.6 缓存一致性与数据库迁移（批 6，33 项）

| 分组 | 关键用例 |
| --- | --- |

## 7. 测试结论

1. 需求规格中定义的全部功能需求均已实现并通过验证，**端到端 414 项断言全部通过、失败 0 项**；单元测试 **后端 192 项 + 管理端 22 项全部通过**；连同前端静态检查共 **666 项通过，仅 1 项为已声明的预期失败**。上述全部由一条命令产出：`python tools/run_all_checks.py --with-unit --with-admin --with-frontend`（实测 133.9s）。
2. 鉴权、越权、参数校验、库存一致性、幂等性、日志脱敏等质量属性均有针对性用例覆盖且通过。
3. 生产化升级轮（批 1–6）新增的配置自检、密码哈希迁移、登录锁定、会话吊销、可观测性、缓存一致性、数据库迁移纳管能力均有独立端到端脚本佐证，且每批都在既有回归全绿的前提下推进，未引入回归。
4. 可观测性验证的关键收获：不仅验证了「功能可用」（指标能读到、健康检查能返回），更验证了「边界正确」——运维端点对匿名与普通用户不可见、未开放端点对管理员也为 404、信息端点不泄露凭证、缓存熔断不误报实例失活。这类「反面断言」比「正面可用」更能暴露配置疏漏。
5. 批 6 的两个取舍值得写进论文：① **分时点验证** —— 微秒级时序用单测精确控制事务同步时点，端到端只验行为与不回归，避免「用端到端断言时序」得到随机结论；② **快照守卫** —— 保留手工建库路径的同时，用脚本把「迁移脚本产出的结构」与「手工建库快照」逐列比对，该守卫当轮就检出了 3 个从未进入任何脚本的漏网字段。
6. 批 7 的收获集中在「测试工程化」本身，三点可直接写进论文：
   - **断言数量不等于覆盖质量**：批 7 之前端到端已有 414 项断言、数字很漂亮，但核心下单 / 支付 / 取消分支的**边界条件**（地址越权、库存恰好不足、影响 0 行、状态被抢先变更）在 HTTP 层无法精确构造 —— 补齐单测后这些分支才第一次被真正覆盖。数字与覆盖是两件事，要分开陈述；
   - **门禁必须区分「失败」与「覆盖不完整」**：一键回归脚本把「测试失败」列为红（影响退出码），把「管理端只跑了 2/3 个测试文件」列入「需留意」（不影响退出码）。若不区分，环境抖动会被误判成代码缺陷；若都算通过，覆盖不完整就会伪装成绿灯 —— 两种误判都会让门禁失去信任；
   - **陈旧的工作流要靠「减少手工步骤」来治，而不是靠纪律**：回归从「手工五步」变成一条命令后，漏跑脚本、跑错实例这两类问题从「靠人记得」变成「结构上不可能发生」。
7. 遗留问题（D-01 ~ D-06）均不影响系统功能正确性与答辩演示，其中 D-03 建议在论文中明确说明，D-04/D-05/D-06 建议在论文「设计与取舍」小节展开。
