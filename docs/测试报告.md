## 1. 测试目的与范围

验证系统是否达成需求规格中定义的功能与质量目标，重点覆盖：

1. 用户端核心链路：登录 → 浏览/搜索 → 购物车 → 下单 → 支付 → 收货 → 评价；
2. 管理端核心能力：图书/分类/订单/用户/评价管理与操作日志；
3. 非功能属性：鉴权与越权防护、参数校验与异常处理、缓存与降级、定时任务幂等、接口文档完整性；
4. 可观测性（批 5 新增）：健康检查、运行信息、指标端点及其鉴权边界、业务埋点计数、结构化日志。
5. 一致性与可部署性（批 6 新增）：缓存清理时机（事务提交后 / 回滚不清理）、数据库迁移由 Flyway 统一纳管并在全新空库上可一键建库。
6. 测试工程化（批 7 新增）：后端核心 Service 层单元测试补齐、管理端引入自动化测试、**一条命令跑完全部回归**。

### 2.1 一键回归（批 7 新增，质量门禁入口）

此前跑一次完整回归需要在终端手工做五件事：起 Redis / MinIO、起后端、等就绪、逐个跑 11 个脚本、自己把「通过 N 项」加起来。手工环节越多越容易漏跑脚本或跑在错误实例上。`tools/run_all_checks.py` 把这条链路固化成一条命令：

```bash
python tools/run_all_checks.py --with-unit --with-admin --with-frontend --with-web   # 质量门禁口径
python tools/run_all_checks.py                                            # 只跑端到端（自动起停服务）
python tools/run_all_checks.py --reuse-server --only=verify_capabilities  # 复用现有实例、只跑指定的几项
```

设计要点（均为实测踩坑后的选择）：

| 要点 | 做法与原因 |
| --- | --- |
| 就绪判据 | 轮询 `/api/category/list` 而**不是** `/actuator/health` —— 后者不查库、恒 200，会出现「端口已监听但数据库没连上」却判为就绪 |
| 服务生命周期 | 默认自己拉起并在收尾 `taskkill /F /T` 整棵进程树；跑单测前必须先停服，否则 `mvn test` 与 `spring-boot:run` 争用 `target/` |
| 汇总行解析 | 11 个脚本历史上格式不一，为每个格式写独立解析器；**解析不到会被标为「异常」而不是悄悄算 0 通过**，避免掩盖问题 |
| 颜色码 | 统一剥离 ANSI 转义序列后再解析 —— vitest 在管道下也照样上色，`Tests  22 passed` 被颜色码切开后正则整行失配 |
| 已知预期失败 | `check_app_sfc.cjs` 的 1 项失败（`common/config.js` 的 `#ifdef` 重复导出）在脚本中显式声明为「允许的预期失败」，汇总中标为 `通过*` |
| 「需留意」与「失败」分开 | 断言数字按实际跑到的如实统计；若检测到「管理端只跑了 2/3 个测试文件」这类**覆盖不完整**，单独列入「需留意」并**不影响退出码** —— 不把环境问题误判成代码问题，也不让不完整覆盖伪装成通过 |
| 报告落盘 | 每次运行写入 `tools/out/regression_<时间戳>.md`，含逐项结果、耗时与备注 |

> **本轮发现并修复的一处真实缺陷**：`BrowseHistoryServiceImpl.upsert` 的返回值把「刷新已有记录的时间」也算作成功，而接口契约（与 `merge` 的调用方语义）写的是**实际新增条数** —— 于是「3 条里已有 1 条」会被回报成「新增 3 条」，前端提示的条数与列表增量对不上。修正为**返回值只表示「新插入了一行」**，时间刷新在方法内部完成；单测相应把原先 `if/else` 容忍两种语义的写法收紧为「断言 `added == 0`」并新增一条混合场景用例（已存在 + 新出现 → `added == 1`）。这条缺陷由端到端脚本抓出，是「端到端与单测互为补位」的直接例证。

## 5. 专项测试
### 5.1 缓存收益（前次实测，方法学已固化）

图书详情接口：冷调用 5.5~6.0 ms → 热调用 3.5~3.9 ms，**耗时降低约 36%**。分类列表提升约 0.8%（数据量小、本就约 1 ms）。

方法学：多次采样取最小值；冷调用前显式删除缓存键强制回源。**不使用"首次调用 vs 中位数"对比** —— 那测到的是 JIT 预热而非缓存收益。

| D-07 | W2 书单数据源从 localStorage 迁到后端时，3 个页面仍在调用已删除的旧 store 方法 | **已修复**。`stores/booklist.js` 重写后 `createBooklist`/`addBooksToList`/`booklists` 已不存在，但 `views/book/list.vue`、`views/search/advanced.vue`、`views/cart/index.vue` 仍按旧签名调用 —— 编译与构建**都不会报错**（运行时才抛），只有全仓检索调用点或点开页面才会暴露。处置：新建 `utils/booklist-action.js` 把「建单 → 加书 → 按 `added` 数提示」收敛为一处，4 个页面（含浏览历史页）统一改用它。**教训：删改 store 方法后必须反向检索调用点，静态检查抓不到这类问题** |

## 7. 测试结论

1. 需求规格中定义的全部功能需求均已实现并通过验证，**端到端 623 项断言全部通过、失败 0 项**；单元测试 **后端 320 项 + 管理端 22 项全部通过**；连同前端静态检查与 PC 商城端到端共 **1016 项通过，仅 1 项为已声明的预期失败**。上述全部由一条命令产出：`python tools/run_all_checks.py --reuse-server --with-unit --with-admin --with-frontend --with-web`（N10 基线实测 195.6s，W2 商城端接入后复测 189.7s，均为 15 项检查，退出码 0）。
2. 鉴权、越权、参数校验、库存一致性、幂等性、日志脱敏等质量属性均有针对性用例覆盖且通过。
3. 生产化升级轮（批 1–6）新增的配置自检、密码哈希迁移、登录锁定、会话吊销、可观测性、缓存一致性、数据库迁移纳管能力均有独立端到端脚本佐证，且每批都在既有回归全绿的前提下推进，未引入回归。
4. 可观测性验证的关键收获：不仅验证了「功能可用」（指标能读到、健康检查能返回），更验证了「边界正确」——运维端点对匿名与普通用户不可见、未开放端点对管理员也为 404、信息端点不泄露凭证、缓存熔断不误报实例失活。这类「反面断言」比「正面可用」更能暴露配置疏漏。
5. 批 6 的两个取舍值得写进论文：① **分时点验证** —— 微秒级时序用单测精确控制事务同步时点，端到端只验行为与不回归，避免「用端到端断言时序」得到随机结论；② **快照守卫** —— 保留手工建库路径的同时，用脚本把「迁移脚本产出的结构」与「手工建库快照」逐列比对，该守卫当轮就检出了 3 个从未进入任何脚本的漏网字段。
6. 批 7 的收获集中在「测试工程化」本身，三点可直接写进论文：
   - **断言数量不等于覆盖质量**：批 7 之前端到端已有 414 项断言、数字很漂亮，但核心下单 / 支付 / 取消分支的**边界条件**（地址越权、库存恰好不足、影响 0 行、状态被抢先变更）在 HTTP 层无法精确构造 —— 补齐单测后这些分支才第一次被真正覆盖。数字与覆盖是两件事，要分开陈述；
   - **门禁必须区分「失败」与「覆盖不完整」**：一键回归脚本把「测试失败」列为红（影响退出码），把「管理端只跑了 2/3 个测试文件」列入「需留意」（不影响退出码）。若不区分，环境抖动会被误判成代码缺陷；若都算通过，覆盖不完整就会伪装成绿灯 —— 两种误判都会让门禁失去信任；
   - **陈旧的工作流要靠「减少手工步骤」来治，而不是靠纪律**：回归从「手工五步」变成一条命令后，漏跑脚本、跑错实例这两类问题从「靠人记得」变成「结构上不可能发生」。
7. W1（新模块后端）的收获有两条值得写进论文：
   - **端到端与单测互为补位，不是替代关系**：本轮 `upsert` 返回值口径的缺陷是**端到端脚本先发现的**（它看到「3 条里已有 1 条」被回报成「新增 3 条」，只有走真实链路才会暴露这种数字不自洽），随后才由单测把契约钉死。单测擅长精确构造边界、端到端擅长发现「各模块各自正确但拼起来不对」的问题；
   - **「能改」与「改完真的生效」是两件事**：配置项若加缓存，后台改完前台仍读旧值，功能看着做了却等于没做。本轮用「改门槛 → 立刻读前台规则」的反向断言把这条链路钉住，并因此在设计上决定 `sys_config` 不加缓存（读取成本可忽略，一致性优先）。
8. W2（商城端前端接入）的收获有两条值得写进论文：
   - **「编译通过」与「跑得起来」是两件事**：把书单 store 的数据源从 localStorage 换成后端后，3 个页面仍在调用已删除的旧方法 —— `vite build` **一次都没有报错**（JS 方法不存在要到运行时才抛），是「反向检索调用点」这个动作把问题揪出来的。重构 store / 工具模块时，必须主动搜调用点，不能依赖构建器；
   - **消费端接入轮必须重跑既有端到端**：本批对前端做了 30 个文件的改动（含 4 个页面的批量操作重写），`verify_web_pc.cjs` 13 项仍全绿，才敢确认「书单迁移」没有连带破坏「对比栏同步」「购物车批量」这些看起来不相关的交互。
9. 遗留问题（D-01 ~ D-07）均不影响系统功能正确性与答辩演示，其中 D-03 建议在论文中明确说明，D-04/D-05/D-06 建议在论文「设计与取舍」小节展开，D-07 可作为「静态检查的盲区」案例写入「测试方法」章节。
